## Oracle

`benchmarks/java-enterprise-route-oracle.ts` is an independent ground-truth extractor: raw
line-based text scan over `src/main/java/**/*.java`, tracking brace depth to find `@Controller`/
`@RestController` classes and their handler methods (mapping-annotated methods at the class's
own brace depth, so nested/anonymous classes can't produce false handlers). It imports nothing
from `src/` — its annotation regex, path-literal extraction, and route composition are written
from scratch, independently of `src/languages/java/enterprise/spring-mvc.ts`.

**Oracle size:** 17 entries for spring-petclinic, 1 for petclinic-rest (18 total).

**Spot-check (manually verified against the checked-out source, not just eyeballing the oracle's
own output):**
1. `OwnerController.initCreationForm` → `GET /owners/new` — confirmed no class-level
   `@RequestMapping` on `OwnerController`; method-level `@GetMapping("/owners/new")` is the whole route.
2. `OwnerController.processUpdateOwnerForm` → `POST /owners/{ownerId}/edit` — confirmed.
3. `PetController.initCreationForm` → `GET /owners/{ownerId}/pets/new` — confirmed
   class-level `@RequestMapping("/owners/{ownerId}")` + method-level `@GetMapping("/pets/new")`
   compose correctly (this is the one real composition case — class prefix + method suffix — in
   either repo).
4. `VetController.showVetList` → `GET /vets.html` and `VetController.showResourcesVetList` →
   `GET /vets` (the latter uses `@GetMapping({ "/vets" })` array syntax and an inline return-type
   annotation `public @ResponseBody Vets showResourcesVetList()`) — both confirmed against source.
5. `WelcomeController.welcome` → `GET /` and `CrashController.triggerException` → `GET /oups` —
   confirmed, both no class-level mapping.
6. `RootRestControllerV1.redirectToSwagger` (petclinic-rest) → `REQUEST /` — confirmed: class-level
   `@RequestMapping("/")` + method-level `@RequestMapping(value = "/")`. This is the **only**
   handler-with-annotation in petclinic-rest at all (see finding below).

**Finding — petclinic-rest is nearly empty of extractable routes, by design of that codebase, not
a bug:** every other REST controller in petclinic-rest (`OwnerRestControllerV1`, `PetRestControllerV1`,
`VetRestControllerV1`, etc.) implements an OpenAPI-generated interface (`OwnersApi`, `PetsApi`, ...)
and puts `@GetMapping`/`@PostMapping`/etc. on that interface, not on the implementing class. The
interface files (`.../rest/api/*Api.java`) are generated at build time and are not present in the
checked-out source, so there is nothing for a source-level, non-compiling extractor to see. This
is an inherent limitation of static regex/text extraction on this delegation pattern, not fixable
without a compiler/JDT dependency (explicitly out of scope, §61-62). Only `RootRestControllerV1`
(a plain, non-generated controller) has real annotations in petclinic-rest.

## Evaluation path chosen

Per the brief's latitude: **I did not extend `benchmarks/benchmark.ts` into a full task-based
route harness.** Reasoning: every existing route-handler-targeted task
(`petclinic-owner-update-explain`, `petclinic-owner-callers`, `petclinic-owner-impact`) already
has a `requiredFacts` entry whose `source-fragment` pattern is the exact composed route string
(e.g. `@PostMapping("/owners/{ownerId}/edit")`, `@GetMapping("/owners/{ownerId}")`). None of these
controllers has a class-level `@RequestMapping`, so the "composed" route is textually identical to
the method-level annotation already present verbatim in the target file — these facts pass by
plain source inclusion regardless of whether `composeRouteContext` fires. Extending the harness
would show a hard-coded 0.0% delta on tasks that were never gated on composition in the first
place, which isn't a real signal, and separately `npm run benchmark` (the harness's replay
command) is currently broken independent of this phase (see regression-gate section) — extending
a broken harness is not a straightforward "quick, real extension." I therefore report route
linkage as this phase's standalone measurement, per the brief's explicit fallback.

I did **not** add new tasks/manual-context entries: per §53, no existing required fact is
currently un-covered by a route composition candidate that this phase's route extraction newly
enables (the one real class+method composition case, `PetController`, has no task targeting it
today, but manufacturing a task purely to exercise composition would be adding scope the plan
didn't ask for — flagged below as a possible, not urgent, follow-up).

### The 3 misses — real bugs, not tuned away

All three are `ANNOTATION_EXTRACTION` (the extractor produced *no* relation at all for a real
handler method), verified by hand against source and index dumps — not extractor logic errors I'm
inferring, but concrete reproductions:

1. **`VisitController.initNewVisitForm` and `.processNewVisitForm`** (both missed). Each handler
   is immediately preceded by a two-line `//` comment
   (`// Spring MVC calls method loadPetWithVisit(...) before initNewVisitForm is\n\t// called`)
   directly above its `@GetMapping`/`@PostMapping` annotation. `parseJava` attributes that
   comment as leading trivia into the method symbol's own `range` (so `range.startLine` points at
   the comment, not the annotation or the `public` keyword). `spring-mvc.ts`'s
   `startsInsideLineComment` guard then checks `line.slice(0, startColumn).includes("//")` at that
   comment line and — because the whole line *is* comment text — wrongly concludes the annotation
   itself is "inside a comment" and skips the entire method. The guard's intent (per its own
   docstring) is only to reject an annotation-shaped *string inside a comment*
   (`// example: @RequestMapping(...)`), but it also fires on a real annotated method that simply
   has an attached leading `//` comment on the line the parser's range starts at. This is a false
   negative in Task 1's confidence/extraction logic, not a fixture artifact — both methods have
   perfectly ordinary, unambiguous route annotations.

2. **`VetController.showResourcesVetList`** (missed). Its annotation is
   `@GetMapping({ "/vets" })` (array-literal syntax) on a method declared as
   `public @ResponseBody Vets showResourcesVetList()` (annotation between the access modifier and
   the return type). Debugging showed the *parser* itself (`src/parser/java-parser.ts`, not
   `spring-mvc.ts`) fails to attach the `@GetMapping({...})` annotation to this method's
   `SymbolRecord.source`/`range` at all — the symbol's captured range starts mid-declaration
   (`" @ResponseBody Vets showResourcesVetList() {"`), with the mapping annotation entirely absent
   from what `spring-mvc.ts` ever sees. This is upstream of the Spring MVC extractor: the
   annotation's `{ }` array-value syntax appears to confuse the parser's own annotation-absorption
   scan, most likely because it also uses `{`/`}` to track structural boundaries elsewhere.

Both are real, reproducible root causes found by this measurement, not inferred from the recall
number alone.

## Fix round 1

Bounded fix-and-remeasure round for the two concrete `ANNOTATION_EXTRACTION` root causes above
(the third miss, `VisitController`, was actually two entries sharing one root cause — see below).
`benchmarks/benchmark.ts` was explicitly left untouched (spun off as its own follow-up task); `npm
test` remained the regression signal throughout, as before.

### Finding 1 — comment guard false-skip (`src/languages/java/enterprise/spring-mvc.ts`)

**Root cause, precisely:** `startsInsideLineComment` checked whether `//` appeared anywhere on the
*symbol's leading-trivia's first physical line* (`fullSource` at `symbol.range.startLine`,
`slice(0, startColumn)`). For `VisitController.initNewVisitForm`/`processNewVisitForm`, that first
line is the tail of an unrelated, ordinary two-line explanatory `//` comment sitting one line above
a completely clean `@GetMapping(...)` annotation — not the annotation being commented out. The
guard fired on the wrong signal (any `//` anywhere in the symbol's leading trivia) instead of its
own documented intent (a `//` on the *same physical line as the annotation match itself*).

**Fix:** replaced the whole-symbol pre-check with `matchIsInsideLineComment(symbol, headerText,
match, fullSource)`, which maps the regex match's position back to the real file (via
`symbol.range.startLine/startColumn` plus the newline count before the match inside the header
text) and checks only *that one physical source line* for a preceding `//`. This required going
back to the real file rather than trusting `symbol.source` alone, because `parseJava`'s own
leading-trivia scan silently strips a commented-out annotation's `//` prefix out of `symbol.source`
itself (confirmed by inspection — for `// example: @RequestMapping("/fake")` the captured source
begins right at the `@`, not the `//`), so checking only the header text can never see that
stripped prefix for the genuinely-commented-out case.

**Regression test:** `tests/java-enterprise-spring-mvc.test.ts`, new test "a real handler preceded
by an ordinary explanatory comment on a previous line is still extracted" — reproduces the exact
VisitController shape (a `//` comment line, then a clean `@GetMapping` line, then the method).

- RED (old guard, confirmed via `git stash` on `spring-mvc.ts` alone + `npx tsx --test
  tests/java-enterprise-spring-mvc.test.ts`): 6 pass, 1 fail — the new test failed with
  `expected a ROUTE_TO_HANDLER relation despite the preceding comment lines`.
- GREEN (fix restored): 7/7 pass, including the pre-existing negative test ("a non-controller class
  with an annotation-shaped string in a comment produces no relation") — confirming the narrowed
  guard still correctly rejects a truly commented-out annotation.

### Finding 2 — inline return-type annotation breaks methodRe (`src/parser/java-parser.ts`)

**Investigation (per the ask to confirm mechanism before touching a shared file):** built two
isolated repros through `parseJava` directly — one with only the `{ "..." }` array-literal
annotation value (`@GetMapping({ "/vets" })`), one with only the inline return-type annotation
(`public @ResponseBody Vets foo()`). Result: the array-literal case parsed perfectly fine on its
own — my original round-0 hypothesis blaming `{ }` braces was **wrong**. The real cause is
`methodRe`'s fixed group order `(annotations)(modifiers)(return type)`: Java allows a return-type
annotation *between* the modifier and the type (`public @ResponseBody Vets foo()`), which the old
regex has no group for. When the match fails to start at `public` for this reason, `matchAll`
retries from the next position and succeeds starting at `@ResponseBody` instead — silently dropping
`public` and the real `@GetMapping(...)` annotation from the captured symbol entirely (confirmed:
`symbol.source` began mid-declaration, at `" @ResponseBody Vets showResourcesVetList() {"`).

**Fix, and what it does *not* do:** added a third, optional group between the existing two
(unchanged) prefix groups and the return type: zero-or-more *extra* interleaved
annotations/modifiers, each requiring a mandatory trailing `\s+` (immediate adjacency, no leading
`\s*`). Groups 1 (annotations) and 2 (modifiers) are byte-identical to the original regex — this
was deliberate after a first draft merged all three into one group and broke
`tests/composition.test.ts`'s Java skeleton test: giving every prefix item its own leading `\s*`
(matching group 1's existing style) let a *plain* `public`-only method with no annotation also
reach backward across a preceding blank line into the previous member's trailing whitespace, which
group 2 never did (group 2 requires immediate adjacency, by original design) — shifting
`symbol.source`'s start into blank trivia and breaking `declarationLine()`'s "first line of
source" logic. The final 3-group design preserves the original two groups' exact match-start
behavior (verified byte-for-byte on `Counter.java`) while accepting the extra interleaved case only
after them. `annotations`/`modifiers` on `SymbolRecord` are derived from groups 1+3 and 2+3
respectively (source-order-preserving), so downstream consumers see no shape change.

**Regression tests:** `tests/parser.test.ts`, two new tests:
1. "captures a method whose declaration has a modifier THEN an inline annotation THEN the return
   type" — the `VetController.showResourcesVetList` shape; asserts the annotation, `public`, and
   correct `annotations`/`modifiers` arrays are all captured.
2. "a plain modifier-only method's captured source is unaffected by the interleaving fix" — the
   `Counter.increment` shape (no annotation at all); asserts `symbol.source` is byte-identical to
   what the pre-merge, pre-fix regex produced, guarding against the exact backward-blank-line
   regression the first draft introduced.

- RED (old `methodRe`, confirmed via `git stash` on `java-parser.ts` alone): test 1 failed, test 2
  passed (2/3 total in that file) — confirming test 2 alone would not have caught finding 2, and
  that both tests together correctly bracket the fix.
- GREEN (fix restored): 3/3 pass in `tests/parser.test.ts`.

**A caching gotcha hit while re-measuring (not a product bug, but worth recording):**
`ProjectIndex.rebuild()` reuses a per-file cached parse from `.context-slice/index.sqlite` when the
*file content* hash is unchanged — correct behavior for normal use, but it meant re-running
`npm run benchmark:v14-phase1` right after the parser fix initially still showed the old 94.4%
(17/18) recall, because the pinned checkouts' stale `.context-slice/index.sqlite` (written during

measurement-environment gotcha specific to re-running the SAME benchmark script immediately after
editing extractor/parser code without a content change to the target repo.
