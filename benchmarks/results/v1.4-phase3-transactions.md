# v1.4 Phase 3, Task 4 — Real-repository measurement: `@Transactional` boundaries

Numbers below come from real runs of `benchmarks/java-enterprise-transactions-oracle.ts` and
`benchmarks/v1.4-phase3-transactions.ts` against the pinned checkouts
(`benchmarks/repositories.json`: `spring-petclinic`, `petclinic-rest`) on 2026-09-27. Nothing here
is hand-edited.

| Repo | `@Transactional(...)` with explicit attribute(s) |
|---|---:|

All 21 are `@Transactional(readOnly = true)` — no other attribute (`propagation`, `isolation`,
`rollbackFor`, `noRollbackFor`, `timeout`) occurs in either pinned repository. This matches the
plan's own grounding section's headline numbers (41 total occurrences including bare ones, 21
with an explicit attribute, all 21 `readOnly = true`), independently re-derived here with fresh
regex code (`benchmarks/java-enterprise-transactions-oracle.ts`), not copied from the plan.

**Correction to the plan's grounding section:** the grounding section states spring-petclinic has
*zero* `@Transactional` usage and that all 41 occurrences are in petclinic-rest. That is not what
direct `grep` (or this oracle) finds: `spring-petclinic`'s
`VetRepository.java` (a `Repository`-extending interface, not a controller/service — likely why
the plan's earlier grep, apparently scoped to controllers/services, missed it) has **2** occurrences
of `@Transactional(readOnly = true)`, on `findAll()` and `findAll(Pageable)`. The plan's headline
totals (41 occurrences, 21 explicit, all `readOnly = true`) are still exactly correct; only the
per-repo attribution in its prose is wrong. spring-petclinic's oracle list is **not** empty — it
legitimately has 2 entries, both of the same `readOnly = true` shape as petclinic-rest's. This is
reported as a real finding per the task instructions, not silently forced to match the plan's
stated expectation.

## Honest scope caveats (per the plan's own grounding section)

- **Only `readOnly` is evidenced by real-repository data.** Both pinned repositories exclusively
  use `@Transactional(readOnly = true)` for every explicit-attribute occurrence. `propagation`,
  `isolation`, `rollbackFor`, `noRollbackFor`, and `timeout` are implemented and exercised by the
  fixture corpus (Task 3) only — never by real-world occurrence in either checkout. This is a
  known limitation of the currently-pinned repositories, not of the extractor.
- **The self-invocation caution (§17)** has no real-repository positive case either — no
  `this.someTransactionalMethod()`-style self-invocation of an explicit-attribute method was
  found in either repo. It remains validated entirely by fixture/unit tests
  (`tests/java-enterprise-transaction-fixtures.test.ts`,
  `tests/java-enterprise-transaction-composition.test.ts`), consistent with the plan's own
  grounding section.
- **spring-petclinic's real sample is thin** (2 entries, both in the same file, same attribute
  shape) — not the "legitimately empty" case the plan's grounding section predicted, but still a
  thin sample that does not by itself broaden real-world coverage beyond `readOnly = true`. Flagged
  explicitly here, the same way Phase 2's Task 4 flagged its own thin field/setter-injection
  sample rather than letting a clean number imply broader coverage than it earned.
