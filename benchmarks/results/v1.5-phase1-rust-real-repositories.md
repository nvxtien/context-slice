## Failure attribution (spec §74)

Failures counted: anchored-unresolved imports, anchored imports resolved to a file the oracle disagrees with, `mod foo;` with no file, resolved-but-name-missing imports, and non-anchored imports marked external that name in-repo code. Rules are deterministic and applied in the order listed in the code:

| category | rule |
| --- | --- |
| PARSER | The importing file, or the file the oracle says is the target, has a tree-sitter syntax error OR was emptied by the adapter (it has no symbols/imports/exports although its text contains items; the indexer reports these as parseErrors). |
| CARGO_WORKSPACE_RESOLUTION | The file belongs to a crate root that is not src/lib.rs or src/main.rs (src/bin/*, tests/*, examples/*, build.rs, or an orphan such as a second crate outside src/), or a non-anchored import names the package's own lib crate but was classified external. |
| RUST_STATIC_LIMIT | The use sits inside an inline `mod x { }` body; or its path continues into an inline mod / item that has no file of its own; or the mod declaration is cfg-gated with no file; or the imported name does not appear anywhere in the resolved file's text. |
| MACRO_EXPANSION_LIMIT | The resolved file contains macro_rules!/an invocation mentioning the imported name and no symbol of that name exists. |
| MODULE_RESOLUTION | The independent oracle finds a file-backed module for the path, but the adapter's modulePathFor disagrees with the oracle module path of that file. |
| USE_RESOLUTION | The oracle finds the target module file and modulePathFor agrees with it, yet the adapter left the import unresolved / resolved it to a different file; or the name appears only inside a `use` group the parser skips (nested use groups); or a non-anchored path names a mod/item/imported name in scope in the same file but was marked external; or a top-level braced `use {a::b, c::d};` was parsed as one import whose module text is the whole group; or the path continues two or more segments past the last file-backed module. |

## Findings

Read the numbers with the failure-attribution table: most of the headline shortfalls trace to one production defect (large files silently emptied), one documented Phase 1 scope limit (multi-target crates), and two gaps in `use` modelling. Nothing here was tuned; the oracle rules were fixed before attribution and UNKNOWN is reported as found.

- **module_resolution_rate.** walkdir 7/7, mini-redis 18/28, ripgrep-ignore 9/13 files agree with the independent oracle. Every disagreement (10 + 4) is a non-lib crate root (`src/bin/*`, `tests/*`, `examples/*`, `build.rs`); MODULE_RESOLUTION disagreements inside the lib/main crate tree: 0 + 0 + 0. The src/lib.rs / mod.rs / foo.rs convention itself is right on real code.
- **use_resolution_rate (anchored).** resolved: walkdir 2/9, mini-redis 51/51, ripgrep-ignore 23/23. But "resolved" is not "resolved correctly": against the oracle, ripgrep-ignore agrees on 13/23; the rest resolved to the wrong file (see defect 1).
- **reexport_resolution_rate.** re-exports with resolvedFile: mini-redis 19/19, ripgrep-ignore 9/9. Non-wildcard re-exports that reach a symbolId: mini-redis 19/19, ripgrep-ignore 0/9 (every one of ripgrep's `pub use crate::walk::...` / `crate::incremental::...` targets is a file the adapter emptied). walkdir has no export records at all, because its `pub use crate::dent::DirEntry` lines live in the emptied `src/lib.rs`.
- **Non-anchored imports** are mostly external and the Cargo.toml oracle backs that up (std-family + declared dependency: walkdir 48/48, mini-redis 112/128, ripgrep-ignore 19/26); the remainder are the defects/limits below. Local-resolved non-anchored imports agree with the oracle 23/23 in mini-redis.
- **Performance.** cold rebuild 65/65/66 ms, warm 8/14/9 ms (walkdir/mini-redis/ripgrep-ignore). Warm and cold resolved values are identical for all three repositories.
- **UNKNOWN.** 1 in mini-redis, 0 in walkdir, 0 in ripgrep-ignore, so the requested five-per-repo inspection was not possible; the single case (`src/connection.rs:88`, `use frame::Error::Incomplete;`) was read by hand: `frame` is bound on line 1 by `use crate::frame::{self, Frame};`, whose `self` item the parser drops, so the adapter calls it an external crate. That is the same defect as defect 4, not an unexplained failure. The other categories were spot-checked against the source as listed below.

## Defects and limitations found

### (a) Production defects (reported, not fixed; `src/` untouched)

1. **Files longer than 32768 characters are silently emptied.** `parseRust` calls `rustParser().parse(source)`; node tree-sitter throws `Invalid argument` for string input over 32 KiB unless `bufferSize` is passed, and `parseRust`'s `catch` returns no symbols/imports/exports with `parseError: true`. Emptied files: walkdir `src/lib.rs` (42415 chars); ripgrep-ignore `crates/ignore/src/dir.rs` (58367 chars), `crates/ignore/src/incremental.rs` (48097 chars), `crates/ignore/src/walk.rs` (93443 chars). The indexer's own cold parseError count matches (1 and 3). Consequences with evidence: walkdir's crate root `src/lib.rs` has zero symbols, so 7/9 anchored imports are unresolved (e.g. `src/dent.rs:7` `use crate::Result;`, `src/error.rs:6` `use crate::DirEntry;`, `src/tests/recursive.rs:5`); in ripgrep-ignore `crate::walk` / `crate::incremental` resolve to `crates/ignore/src/lib.rs` through the containing-module fallback instead of `walk.rs` / `incremental.rs` (`crates/ignore/src/lib.rs:51-52`, `pathutil.rs:3`), and 9/9 `pub use` re-exports there carry no symbolId. The failure is a wrong answer, not an error, and it is the largest single source of failures in this benchmark. Real-world crate roots are frequently larger than 32 KB.
2. **Private `use` chains are not followed.** `mini-redis/src/lib.rs:41-50` has `use db::Db;`, `use parse::{Parse, ParseError};`, `use shutdown::Shutdown;` (non-`pub`, visible to descendants). Imports such as `use crate::{Connection, Db, Frame, Parse};` (`src/cmd/get.rs:1`) resolve to `src/lib.rs` but the imported name is not a symbol or export there: 20 such cases in mini-redis (precision proxy 72.97%). Only `pub use` creates an ExportRecord.
3. **Top-level braced `use { a::b, c::d };` is mis-parsed.** `crates/ignore/src/gitignore.rs:17`, `types.rs:89`, `examples/walk.rs:3` produce one import whose `module` is the whole brace group text (newlines included), marked external; the real imports are lost.
4. **A non-anchored path whose first segment is bound locally is called an external crate.** `use Command::*;` (`mini-redis/src/cmd/mod.rs:96`), `use ParseError::EndOfStream;` (`cmd/set.rs:81`, `cmd/subscribe.rs:62`, `:310`), `use frame::Error::Incomplete;` (`connection.rs:88`). Related: `self` inside a use group (`use crate::frame::{self, Frame}`) is not recorded as a binding, and nested use groups are skipped by design.

### (b) Known, documented limitations (workspace / bin / inline-mod / `#[path]`)

- Every `src/bin/*.rs`, `tests/*.rs`, `examples/*.rs` and `build.rs` is its own crate root but gets a src-relative module path (mini-redis 10, ripgrep-ignore 4 files; e.g. `src/bin/cli.rs` -> [bin, cli]). Their imports of the package's own library (`use mini_redis::...`: 11 in mini-redis; 4 in ripgrep-ignore) are classified external although the crate is in the repository.
- `walkdir/walkdir-list/main.rs` is a second crate outside `src/` and stays an orphan.
- Imports inside inline `mod tests { use super::X; }` are resolved at file granularity: `crates/ignore/src/default_types.rs:350` `use super::DEFAULT_TYPES` resolves to `lib.rs` although `super` of the inline module is `default_types.rs` (6 cases in ripgrep-ignore, RUST_STATIC_LIMIT).
- `#[path]`, cfg-gated modules and macro-generated modules are not modelled; none of them occurred in these three repositories (skipped-path-attribute 0, missing-file declarations 0), so this benchmark says nothing about them.

### (c) Oracle limitations

- Crate roots are inferred from directory conventions, not from Cargo.toml `[[bin]]`/`[lib] path`; `examples/*.rs` was added to the plan's root list (Cargo treats them as crates).
- `targetContainsName` is a proxy: it checks symbols, exports and enum-variant text in the resolved file, so private-`use` names and items generated by macros count as "missing"; it is not ground truth.
- Attribution rules are heuristic text rules (see the table); an import inside an inline module or a function body is evaluated at file granularity.
- Cargo.toml dependency detection is line-based and ignores renames and workspace-inherited tables.
- Three repositories (one sparse workspace member) are a small sample; percentages on small denominators (walkdir: 9 anchored imports) are not statistically meaningful.
