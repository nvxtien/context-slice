# v1.6 — Go support, Phase 3a real-repo benchmark

Real-repo symbol, import, export-visibility, and call-extraction benchmark for
the Go adapter (`parseGo`), run against three pinned checkouts of varying scale:

| repo | scale | kind | symbols found / total | imports found / total | calls found / total | resolutions matched / total | supertypes matched / total |
|---|---|---|---|---|---|---|---|
| [pkg/errors](https://github.com/pkg/errors) | small | library (error-wrapping) | 21/21 | 2/2 | 5/5 | 5/5 | 0/0 |
| [spf13/cobra](https://github.com/spf13/cobra) | medium | library (CLI framework) | 12/12 | 3/3 | 4/4 | 5/5 | 0/0 |
| [go-chi/chi](https://github.com/go-chi/chi) | large | library (HTTP routing) | 13/13 | 3/3 | 5/5 | 9/9 | 3/3 |

**46/46 (100%)** of the hand-curated symbol oracle, **8/8 (100%)** of the
hand-curated import oracle, and **14/14 (100%)** of the hand-curated call
oracle were found.

Phase 1's symbol-kind coverage (functions, methods, structs/`class`, interfaces,
type aliases, top-level variables, struct fields) is unchanged and still at 100%
with no regressions. Phase 2 adds:

- **Export visibility**: every existing oracle entry now carries `exported: true`
  (each was already a capitalized, genuinely-exported identifier), and each repo
  gained one new `exported: false` entry for a real unexported identifier read
  directly from source — `callers` (pkg-errors/stack.go:163), `stripFlags`
  (cobra/command.go:674), `chain` (chi/chain.go:36). The comparison now checks
  `modifiers.includes("exported")` against the oracle's `exported` flag wherever
  it's specified.
- **Imports**: a new `imports` oracle map with 2-3 real, hand-verified import
  entries per repo — `fmt`/`io` (pkg-errors/errors.go), `context`/`errors`/`os`
  (cobra/command.go), `net/http`/`context`/`sync` (chi/chi.go, chi/mux.go). All are
  plain package imports, so the adapter emits `kind: "namespace"` for each, matched
  against `index.imports` by module + kind.

Every new entry was read directly from the checked-out source during this task's
own execution and confirmed to exist exactly as named/kinded before being added, so
this run hit 100% on both symbols and imports on the first pass with no adapter
fixes needed.

Phase 3a adds call-edge extraction (Task 1: `src/languages/go/parse.ts`,
`collectCalls`/`buildCallEdge`) and this benchmark's coverage of it (Task 2): a new
`calls` oracle map with 4-5 real call sites per repo, hand-read from the same
checkouts and chosen to exercise `calleeName`s the symbol/import oracles above
don't already name — a mix of direct (bare) calls, selector/method calls on a
local receiver, and package-qualified stdlib calls:

- **pkg-errors**: `fmt.Sprintf` (errors.go:114), `io.WriteString` (errors.go:131),
  `runtime.FuncForPC` (stack.go:24), `strings.LastIndex` (stack.go:173), and the
  direct call `callers()` (errors.go:105, inside `New`).
- **cobra**: `c.getOut(...)` (command.go:394), `c.mergePersistentFlags()`
  (command.go:678), `strings.HasPrefix` (command.go:691), and the direct call
  `stripFlags(innerArgs, c)` (command.go:761).
- **chi**: `mx.NotFoundHandler()` (mux.go:66), `mx.handle(...)` (mux.go:116),
  `strings.IndexAny` (mux.go:110), `strings.TrimLeft` (mux.go:111), and the direct
  call `chain(mx.middlewares, http.HandlerFunc(mx.routeHTTP))` (mux.go:526).

Each is matched against `index.calls` by `calleeName`, and by `receiverText` too
wherever the oracle entry specifies one; a direct-call entry omits `receiverText`
and so only needs the adapter's `fnNode?.type === "identifier"` path in
`buildCallEdge` to fire correctly, since a selector-call entry would never
exercise it. All 14 were found on the first run with no adapter fixes needed, and
no existing symbol/import oracle entry regressed.

## Phase 3b (Task 4): call-resolution accuracy

Builds on Phase 3a's call-extraction oracle with a new `resolutions` oracle (16
entries, 5-6 per repo) that checks `resolveGoCalls`' actual output —
`resolutionKind`/`externalPackage` — against the semantically-correct ground
truth for specific, disambiguated call sites (matched by `calleeName` +
`receiverText` + `filePath` + line, since the same callee name recurs dozens of
times in a real repo). **16/16 (100%)** matched; existing symbol/import/
call-extraction entries are untouched and still 100%.

- **pkg-errors (5/5)**: this repo has no `go.mod` and a single flat directory
  (no subpackages), so every package-qualified call it makes is necessarily
  external — `fmt.Sprintf`, `io.WriteString`, `runtime.FuncForPC`,
  `strings.LastIndex` all correctly stay `unresolved` with `externalPackage`
  set to the stdlib package name, and the direct call `callers()` (errors.go:105)
  correctly resolves `same-file`.
- **cobra (5/5)**: `c.getOut(...)` (command.go:394, inside method
  `OutOrStdout()`) and `c.mergePersistentFlags()` (command.go:1220, inside
  method `InitDefaultHelpFlag()`) both correctly resolve `same-type` via the
  receiver-matches-caller fast path. `strings.HasPrefix` (command.go:691)
  correctly stays `unresolved` (external). The direct call `stripFlags()`
  (command.go:761) correctly resolves `same-file`. `cobra.WriteStringAndCheck(...)`
  in the real `doc/` subpackage (doc/man_docs.go:149) correctly resolves
  `imported` to the exported function at the module root (cobra.go:243) — the
  one clean same-module import-qualified example found across all three repos.
- **chi (6/6)**: `mx.NotFoundHandler()` and `mx.handle(...)` (mux.go:66,116,
  inside methods on `(mx *Mux)`) both correctly resolve `same-type`.
  `strings.IndexAny`/`strings.TrimLeft` (mux.go:110-111) correctly stay
  `unresolved` (external). The direct call `chain(...)` (mux.go:526) correctly
  resolves `same-file`.

  **Previously a genuine miss, now fixed**: `chi.RouteContext(...)` in
  `middleware/clean_path.go:14` is a real cross-package internal call —
  `middleware/` imports chi's own module path (`github.com/go-chi/chi/v5`) and
  calls the exported `RouteContext()` declared at the module root
  (context.go:25) — and should resolve `imported`. It previously didn't:
  `resolveGoCalls`' `importLocalName()` fell back to `module.split("/").pop()`
  for an unaliased import, which yielded `"v5"` for this module path, not
  `"chi"` (the real package-clause name declared in chi.go). Since the call's
  `receiverText` is `"chi"`, the import lookup in `resolveQualifiedCall()`
  never found a match, so the call fell through unresolved — and because the
  mismatch happened before the internal/external branch, without even
  `externalPackage` set. This affected any Go module using the standard
  major-version-suffix convention (`.../v2`, `.../v3`, ... — common for any
  module at major version 2+), not just chi. Fixed in `importLocalName()` by
  stripping a trailing `/v\d+` segment from the module path before taking its
  last path segment, so `github.com/go-chi/chi/v5` resolves to local name
  `"chi"` for an unaliased import, matching Go's own package-naming
  convention. `chi.RouteContext(...)` now correctly resolves `imported`.

## Phase 4 (Task 4): struct embedding / interface-satisfaction coverage

Extends the benchmark with real examples of struct embedding, method
promotion, and interface satisfaction (`supertypes`), per Phase 4's Tasks 1-3
(`src/languages/go/parse.ts`'s `metadata.embedded`/`interfaceMethods`,
`src/languages/go/resolve.ts`'s `findPromotedMethod`/
`resolveInterfaceSatisfaction`). Searched honestly across all three checkouts
first — struct embedding and interface satisfaction are **not evenly
distributed**: pkg-errors and cobra have none of the specific pattern this
phase targets (struct-embeds-struct), while chi has several genuine,
unforced examples.

**pkg-errors and cobra: no struct-embeds-struct found.** pkg-errors'
`fundamental` and `withStack` (errors.go:120,155) do embed fields — `*stack`
and the builtin `error` interface — but `stack` is `type stack []uintptr`
(stack.go:140), a slice-alias type (`kind: "type"`), not a struct
(`kind: "class"`), and `error` is a builtin interface, not a locally-declared
struct either. Neither can produce a struct-embedding `supertypes`/promotion
case under this phase's design (`embeddedTypesOf` only matches siblings of
`kind === "class"`). cobra's structs (`Command`, `Group`, `CompletionOptions`,
etc.) have no embedded fields at all. A correct "0/0 supertypes" oracle for
both repos is honest evidence, not an omission.

**chi: 3/3 real `supertypes` examples found, all hand-verified by reading the
actual source and then confirmed by running the indexer directly:**

- `Mux` (mux.go) → `supertypes: ["Router", "Routes"]` — **direct** satisfaction,
  no embedding: `Mux` defines every method both `Router` and `Routes`
  (chi.go:68,121) require directly (`ServeHTTP`, `Use`, `Handle`, ...,
  `Routes()`, `Middlewares()`, `Match()`, `Find()` — all present in mux.go).
- `basicWriter` (middleware/wrap_writer.go:74) → `supertypes:
  ["WrapResponseWriter"]` — **direct**: defines `Status`/`BytesWritten`/
  `Tee`/`Unwrap`/`Discard` itself, the 5 methods `WrapResponseWriter`'s own
  `interfaceMethods` list requires (its embedded `http.ResponseWriter` is
  excluded from that list by `parse.ts`'s `method_elem`-only filter).
- `flushWriter` (middleware/wrap_writer.go:151) → `supertypes:
  ["WrapResponseWriter", "compressFlusher"]` — **promotion-driven**:
  `flushWriter` embeds `basicWriter` and only defines `Flush()` itself;
  `WrapResponseWriter` is reached through `methodSetOf`'s embedding walk into
  `basicWriter`. `compressFlusher` (compress.go:353, `interface { Flush()
  error }`) is also matched — genuine evidence of a **pre-existing,
  signature-blind limitation** (not introduced or fixed by this task):
  `interfaceMethods`/`methodSetOf` compare method *names* only, never
  signatures, so `flushWriter.Flush()` (no return value) is treated as
  satisfying `Flush() error` even though Go's real type checker would reject
  it. Recorded as found, not suppressed.

**chi: 2 new genuine positive call-resolution examples** (Task 2's
struct-embedding method promotion, `findPromotedMethod`), extending the
`resolutions` oracle from 6 to 9 entries:

- `f.BytesWritten()` at middleware/wrap_writer_test.go:196 and :219 — both
  inside tests that bind `f` via an explicit struct literal
  (`f := &httpFancyWriter{basicWriter: basicWriter{...}}`), so
  `bindingTypeInBody` infers the concrete struct `httpFancyWriter`.
  `httpFancyWriter` doesn't define `BytesWritten()` itself — only
  `basicWriter` does — so both correctly resolve `same-type` via one level of
  embedding promotion. **Confirmed positive**, not just the negative/gap
  cases documented in Phase 3b above.

**1 new genuine, honest miss** (documented, not fixed — out of this task's
scope): `ww.Status()` / `ww.BytesWritten()` at middleware/logger.go:52, where
`ww := NewWrapResponseWriter(w, r.ProtoMajor)`. `bindingTypeInBody`'s
ctor-name fallback (`ww := New<Type>(`) infers the type from the *function
name*, yielding `"WrapResponseWriter"` — the constructor's declared
**interface** return type, not any of the concrete structs it actually
returns at runtime (`basicWriter`/`flushWriter`/`hijackWriter`/etc., chosen
by a type switch). Since `"WrapResponseWriter"` is `kind: "interface"`, not
`"class"`, the struct lookup in `resolveMethodCall` fails before promotion
can even be attempted, and the call correctly stays `unresolved`. This is a
real scope limit of the ctor-name heuristic on any factory whose name
doesn't match its concrete return type — a legitimate, not-fixed gap,
scored as a miss rather than papered over, same discipline as the
versioned-module-path gap in Phase 3b.

**19/19 (100%)** of the full `resolutions` oracle (16 existing + 3 new) and
**3/3 (100%)** of the new `supertypes` oracle matched. All prior symbol/
import/call-extraction/resolution entries are unchanged and still at 100%.
