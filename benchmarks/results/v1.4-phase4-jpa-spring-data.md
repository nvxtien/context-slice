## The plain-interface finding (petclinic-rest)

Confirmed, independently re-derived, and quantified precisely: **10 derived-query methods across
6 files** (`OwnerRepository`, `PetRepository`, `PetTypeRepository`, `SpecialtyRepository`,
`VetRepository`, `VisitRepository`) are declared on a "plain" repository interface with no
`<Entity, Id>` generic of its own — `findByLastName` (×2 overloads) and `findById` on
`OwnerRepository`, `findById` on `PetRepository`, `findById`/`findByName` on `PetTypeRepository`,
`findById` on `SpecialtyRepository`, `findById` on `VetRepository`, `findByPetId`/`findById` on
`VisitRepository`. This count exactly matches the number quantified by two independent prior
reviews during Tasks 1-2.

Of those 10, only **3** (`OwnerRepository`'s `findByLastName` × 2 and `findById`) were also
re-declared with `@Override` on the sibling `SpringDataOwnerRepository` (which does carry
`Owner, Integer`) — so those 3 already got a `REPOSITORY_QUERY` relation pre-fix, just attributed
to the override's own method symbol, not the plain interface's. The other **7** (`Pet.findById`,
`PetType.findById`, `PetType.findByName`, `Specialty.findById`, `Vet.findById`,
`Visit.findByPetId`, `Visit.findById`) have **no** re-declaration anywhere — their sibling
`SpringData*Repository` interfaces are either empty or only override unrelated methods
(`findAll(Pageable)`, `delete(...)`). Those 7 got **zero** `REPOSITORY_QUERY` relations under the
pre-fix extractor, exactly as diagnosed.

Separately, this task's own measurement surfaced **2 more** real misses the prior diagnosis didn't
name: `Owner.findAll(Pageable)` and `Pet.findAll(Pageable)` are declared on both the plain
interface (no `@Query`) and the `SpringData*Repository` override (with `@Query`), but the
override method's `SymbolRecord.source` does not include its own leading `@Override`/`@Query`
annotations (a parser-level fact, confirmed by direct inspection — `source` for that symbol is
exactly `"Page<Owner> findAll(Pageable pageable);"`), so `queryText()` finds nothing and, since
`findAll` doesn't match the derived-query name pattern either, no relation is produced. This is a
**different** mechanism from the plain-interface gap (it is about annotation capture in
`src/parser/java-parser.ts`'s method `source` field, not about interface-shape propagation) and
was left unfixed — see "Scope decision" below.

## Investigation and fix

**Root cause:** `spring-data.ts`'s `repositoryShape()` only recognizes an interface that itself
carries the `<Entity, Id>` generic. A plain supertype interface's own derived-query methods are
never visited during per-file extraction, regardless of whether a sibling subinterface later
re-declares them.

**Fix (narrow, `spring-data.ts` only, confirmed no `java-parser.ts` change needed):** added a new
resolver, `resolveRepositoryQueryPropagation`, registered after the existing `resolvePersistsEntity`.
Once an interface's `PERSISTS_ENTITY` has resolved with `confidence: "exact"`, the resolver walks
that interface's own `SymbolRecord.supertypes` (already populated by the parser as plain
identifiers, generics already stripped) and, for every supertype that resolves to exactly one
project interface with **no** generic shape of its own (never guessed — ambiguous or
framework/external names are skipped, same discipline as `resolvePersistsEntity`), runs the exact
same derived-query/`@Query` extraction on that supertype's own methods, attributing the resulting
`REPOSITORY_QUERY` relations to the same entity the subinterface resolved. This required no change
to `src/parser/java-parser.ts` — `SymbolRecord.supertypes` already existed and already gave plain
identifiers, so `INDEX_VERSION` was not bumped.

## Oracle design

- Independent, `src/`-free regex scan (`benchmarks/java-enterprise-jpa-oracle.ts`), mirroring
  every prior phase's oracle-independence discipline.
- `entity_relation` oracle: `@Entity` classes, field-level `@OneToOne`/`@OneToMany`/`@ManyToOne`/
  `@ManyToMany` with explicit `mappedBy`/`fetch`/`cascade`/`@JoinColumn` only.
- `repository_linkage` oracle: for every interface whose own `extends` clause carries a known
  Spring Data base with a 2-argument `<Entity, Id>` shape, walks its plain (non-generic) supertype
  interfaces too (same technique the fix applies in production), collecting derived-query/`@Query`
  methods deduped by `(methodName, paramCount)` across every interface that declares them. This
  is a deliberate design choice: `repository_linkage`'s ground truth is "this entity's repository
  has this queryable method" as a fact about the entity, not about a single symbol — matching how
  §22-23 frame repository linkage, and matching the propagation fix's own semantics. Grading
  credits a match if **any** of the fact's declaring symbols carries the relation.
- `PERSISTS_ENTITY` + `REPOSITORY_QUERY` are graded together as one `repository_linkage` pair
  (not split further) because `REPOSITORY_QUERY` only exists once `PERSISTS_ENTITY` has resolved
  its owning interface — they are two facts about the same mechanism, not two mechanisms.
- Spot-checked (well over the required 5 per repo): all 3 `persistsEntity` entries in
  spring-petclinic and all 7 in petclinic-rest were manually cross-checked against the real
  checkout source (interface names, `extends` clauses, `<Entity, Id>` arguments) during this
  task's investigation; 3 `entityRelations` samples per repo were read directly against
  `Owner.java`/`Pet.java` source in both repos (field names, `mappedBy`/`fetch`/`cascade`/
  `@JoinColumn` values) and matched exactly.

## Honest scope caveats (per the plan's own grounding section)

- **Compound (`And`/`Or`) derived-query predicates are fixture-only.** Neither pinned repository
  has a single real `findByXAndY`/`findByXOrY`-style method — every real derived-query method in
  both repos is a single-property predicate (`findByLastName`, `findByName`, `findByPetId`, ...).
  The `And`/`Or` word-boundary split logic is validated by `tests/fixtures/java-enterprise/
  JpaRepositoryDerivedQuery.java` only, not by real-world occurrence.
- **Bidirectional `mappedBy` relationships have exactly one real-repository occurrence**
  (`Owner.pets` in petclinic-rest, `mappedBy = "owner"`) — everything else with an explicit
  `mappedBy` in the fixture corpus (`JpaEntityBidirectional.java`'s `Invoice`) is fixture-only.
  spring-petclinic's `Owner.pets` uses `@JoinColumn` instead (unidirectional-style mapping), so it
  does not add a second real `mappedBy` sample.
- **The annotation-capture gap on `@Query`-only, non-`findBy`-named methods** (`findAll(Pageable)`
  on 2 files) is a real, confirmed finding from this run, left unfixed because its root cause is
  in the shared `src/parser/java-parser.ts` (method `SymbolRecord.source` not including leading
  annotations for these particular interface-method declarations) — out of this task's scoped
  fix, per the brief's shared-file caution, and orthogonal to the plain-interface finding this
  task was asked to specifically investigate. `repository_linkage_recall` already clears the
  ~90% bar without fixing it.
- **The 2 pre-existing `PERSISTS_ENTITY` false positives** (bogus `can`-named interface symbols in
  spring-petclinic's `OwnerRepository.java`/`VetRepository.java`, from an existing
  `java-parser.ts` regex quirk on javadoc text) are unrelated to and unchanged by this task's fix;
  also out of scope for the same reason.
