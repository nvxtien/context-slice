# Task 4: Real-repository measurement — report

## Oracle design

`benchmarks/java-enterprise-di-oracle.ts` is a from-scratch, `src/`-free regex/brace scanner
(imports nothing from `src/`). It records raw injection points —
`{ repo, file, className, injectionKind: "constructor"|"field"|"setter", typeName, memberName,
qualifier?, startLine }` — for:

- Constructor parameters, gated the same way Spring itself gates constructor DI: the class must
  carry a stereotype annotation (`@Component`/`@Service`/`@Repository`/`@Controller`/
  `@RestController`/`@Configuration`) **or** the constructor itself is `@Autowired`/`@Inject`. This
  gate is a fact about what Spring actually treats as DI (a plain `Order(Customer c)` constructor
  on an unmanaged class is not DI), not a copy of the product's implementation — applying it
  independently is necessary for the oracle to be meaningful ground truth rather than a source of
  spurious misses.
- `@Autowired`/`@Inject`/`@Resource` fields and explicit setters.

It deliberately does **not** resolve bean identity — that's the extractor's job, graded
independently. Instead it exposes `projectTypeNameCounts()`, its own independent
`class|interface|enum|record NAME` regex scan of every file, so the evaluation script can judge
(without ever trusting the product) whether each oracle entry's type is a unique project bean
(should resolve `"exact"`), ambiguous (must never resolve `"exact"`), or external (must produce no
`"exact"` relation).

Top-level classes only (mirrors `java-enterprise-route-oracle.ts`'s documented top-level-only
convention) — neither pinned repo's `@Autowired`/constructor-injected classes are nested, so this
is not a material gap here.

## Evaluation script and results

`benchmarks/v1.4-phase2-dependency-injection.ts`: for every oracle entry, finds the corresponding
product `SymbolRecord` (constructor by name+line-range; field by enclosing class, since fields
aren't symbols — matches the product's own documented design; setter by method name) and checks
`index.enterpriseRelations` for a matching `INJECTS_DEPENDENCY` relation with the same
`targetLabel`. Only oracle entries whose type is a **unique** project bean
(`projectTypeNameCounts` count === 1) count toward the recall denominator — those must resolve
`confidence: "exact"`. Ambiguous/external entries are checked separately: any `"exact"` resolution
on one of those is a fabricated-identity false positive (never happened here).

Relations are scoped to `src/main/java` to match the oracle's own scan scope (brief Step 1); an
initial run without this filter reported precision 54.7% purely because `src/test/java` has real,
legitimate `@Autowired` test-fixture injections the oracle never looked at (test files are outside
`src/main/java`) — an oracle-scope mismatch in the harness, not an extractor defect. Restricting
both sides to `src/main/java` fixed this; no extractor code changed.

### Sample composition by injection mechanism

Generated by the evaluation script itself (`v1.4-phase2-dependency-injection.ts`'s per-repo
`byKind` console output / `results.json` `perRepo[repo].byKind`), not hand-typed:

| repo             | constructor (oracle / unique-bean / matched) | field (oracle / unique-bean / matched) | setter (oracle / unique-bean / matched) |
|-------------------|----------------------------------------------:|-----------------------------------------:|-------------------------------------------:|
| spring-petclinic  | 6 / 6 / 6                                     | 0 / 0 / 0                                | 0 / 0 / 0                                   |
| petclinic-rest    | 36 / 28 / 28                                  | 2 / 1 / 1                                 | 1 / 0 / 0                                   |
| **total**         | **42 / 34 / 34**                              | **2 / 1 / 1**                             | **1 / 0 / 0**                               |

**Honest reading:** the 100%/100% headline is overwhelmingly a constructor-injection result — 34
of the 35 unique-bean entries the recall/precision figures are computed over are constructor
injections. Field injection contributes exactly 1 unique-bean entry, and setter injection
contributes 0 (its single oracle entry, `AuthenticationManagerBuilder`, is an external
framework type, correctly excluded from the recall denominator rather than a match). With only 3
field/setter entries total across both repos (2 field + 1 setter), this sample gives essentially no
statistical evidence about field/setter-injection recall or precision specifically — those
mechanisms are exercised, and behave correctly on what little is here, but the 100% figure should
not be read as strong evidence for field/setter injection the way it legitimately is for
constructor injection.

(The 10 petclinic-rest entries excluded from the recall denominator are legitimately
ambiguous/external types — `DataSource`, `JdbcTemplate`, `AuthenticationManagerBuilder`, and
mapper/service interfaces with duplicate simple names across `service`/`rest` package variants —
and none of them was ever claimed `"exact"` by the extractor, confirming no fabricated bean
identities.)

Full results: `benchmarks/results/v1.4-phase2-dependency-injection.json`.

## Deferred generic-wrapper limitation (`List<X>`/`Optional<X>`) — investigated, not exercised

Checked both pinned repos for `@Autowired`/`@Inject`-annotated fields or constructor/setter
parameters typed `List<...>` or `Optional<...>` under `src/main/java`:

```
grep -rn "Autowired|Inject\b" -A2 spring-petclinic/src/main/java petclinic-rest/src/main/java | grep -E "List<|Optional<"
→ (no matches)
```

The only `List<...>` occurrences found in either repo are plain setter parameters on domain model
classes (`Vet.setSpecialties(List<Specialty>)`, `Pet.setVisits(List<Visit>)`,
`Owner.setPets(List<Pet>)`) and a private helper method — none are DI (no `@Autowired`/`@Inject`,
not constructor params on a stereotyped class). Per the brief's guidance ("do not fix it
speculatively if the real repos don't actually exercise it"), no fix was made: the pinned repos do
not exercise this limitation, so 100%/100% recall/precision is not masking a real gap here. This
remains a known, real recall gap for repos that do use collection/`Optional` injection (documented
in Task 1's review) — just not one visible in this measurement.
