# v1.7 — JavaScript Support Benchmark

Validates the JavaScript adapter (`src/languages/javascript/`, which
reuses `parseTypeScript`/`resolveTypeScriptCalls` as-is) against two
real, pinned repositories chosen specifically to cover both of
JavaScript's two module systems:

| Repo | Scale | Module system | Commit |
|---|---|---|---|
| [expressjs/express](https://github.com/expressjs/express) | medium (~50 `.js` files) | CommonJS (`require()`/`module.exports`) | `7ef98448` |
| [sindresorhus/chalk](https://github.com/sindresorhus/chalk) | small (~8 `.js` files) | ESM (`import`/`export`) | `47fc05ab` |

## Results

| Repo | Symbols | Imports | Exports | Calls |
|---|---|---|---|---|
| express | 3/3 | 0/0 | 0/0 | 3/3 |
| chalk | 4/4 | 3/3 | 2/2 | 1/1 |

All oracle entries were read directly from the real checked-out source
and cross-checked against the adapter's actual output (via a throwaway
probe script) before being written into the oracle — not guessed.

## Known, confirmed gap: CommonJS import/export is invisible to this adapter

`express`'s import/export oracle is correctly **0/0**, not skipped or
N/A. The JS adapter reuses `parseTypeScript` unchanged — its import/export
extraction only recognizes ES `import_statement`/`export_statement` grammar
nodes. A CommonJS `require('./foo')` is an ordinary `call_expression`
to this grammar, and `module.exports = x` / `exports.y = z` are ordinary
`assignment_expression`s — neither is special-cased, so **zero**
`ImportRecord`/`ExportRecord`s are ever produced for CommonJS-style code,
confirmed directly against express's real `lib/express.js` (`var
bodyParser = require('body-parser')`, `exports = module.exports =
createApplication`) during this benchmark's own writing.

This means: for a CommonJS-heavy real-world JS codebase (still very common
in Node.js backend code, as express itself demonstrates), context-slice's
cross-file import/export resolution features will not work at all —
only symbol extraction and same-file/in-scope call extraction do. Symbol
extraction itself is unaffected: `createApplication`, `logerror`,
`tryRender` etc. are all correctly extracted as top-level `function`
symbols regardless of module system, since that detection has nothing to
do with import/export syntax.

A related, separately-confirmed limitation: the dominant express
authoring pattern `app.init = function init() {...}` (assigning a named
function expression to an object property) does **not** produce its own
symbol — only genuine top-level `function NAME(...)` declarations and
`var`/`let`/`const` declarations are extracted as symbols. This is a
pre-existing TypeScript-adapter behavior (inherited as-is by JS, not
something this benchmark's JS work changed), confirmed directly against
the adapter's real output, not assumed.

## What this benchmark does NOT cover

- CommonJS import/export resolution (confirmed broken, not benchmarked
  further since there is nothing to measure — it produces zero records,
  consistently).
- JSX parsing on a real project (unit-tested in `tests/javascript.test.ts`
  but not exercised against a real `.jsx` codebase here — no suitable
  small, real, plain-JavaScript-not-TypeScript JSX repository was found
  during this benchmark's scope).
- Call *resolution* accuracy (only *extraction* is measured here) — JS
  reuses the same `resolveTypeScriptCalls` already benchmarked
  extensively in `v1.1-typescript-support.ts` for `.ts`/`.tsx` files, so
  no new resolution logic was built or needs separate validation; this
  benchmark exists to confirm the JS *adapter wiring* itself works on
  real `.js` files, not to re-validate resolution logic already proven
  on TypeScript.
