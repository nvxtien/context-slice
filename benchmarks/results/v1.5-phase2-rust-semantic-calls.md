## Performance of call extraction
Measured in the Task 6 review, not by this script: `parseRust` with call extraction is +65-69% slower than the Phase 1 parser on real files (ripgrep-ignore `dir.rs` 26.5 -> 44.7 ms, `walk.rs` 43.5 -> 73.1 ms, `incremental.rs` 23.1 -> 38.2 ms; synthetic 1 MiB file 1117 -> 1792 ms), linear in file size. Cause: a second tree traversal; merging the traversals is deferred.

Rebuild cost vs `main` (no Rust call resolution), measured after the final run with a scratch script (full rebuild of a temp copy, same machine; warm = second rebuild of an unchanged tree). The indexer re-resolves every unresolved or external Rust edge on every rebuild (`src/indexer/index.ts`, shared rebuild path), so warm rebuilds pay the resolver again:

| repo | main cold / warm ms | final-run commit cold / warm ms | after the perf fix cold / warm ms |
|---|---|---|---|
| walkdir | 87-93 / 7-12 | 207-213 / 60-66 | 204-218 / 29-38 |
| mini-redis | 115-119 / 12-14 | 218-226 / 75-82 | 215-219 / 34-45 |
| ripgrep-ignore | 197-202 / 19-22 | 558-569 / 242-255 | 490-497 / 96-123 |

So cold rebuilds are about 2.2-2.5x and warm rebuilds about 3-5x slower than `main` after the fix (before it: cold 2.5-2.9x, warm 6-12x). The fix (a per-file cache for a whole-file text scan that ran on every glob lookup, an index of top-level symbols by name, and parse trees reused across rebuilds while the text is unchanged) made resolution roughly linear in file size: a generated single `lib.rs` of 122K/244K/488K/976K chars went from 0.8/2.1/6.1/20.4 s cold to 0.55/1.0/1.9/4.1 s cold (warm 0.3/0.8/2.6/8.8 s -> 0.1/0.16/0.32/0.77 s). Every Rust edge of the three checkouts is byte-identical before and after the fix (cold and warm), so the measured tables above are unaffected.

## Honesty notes and known limits
- Thin samples: pooled headline n=74 (dev 45, held-out 29). Per-repo and per-category held-out rates rest on a few entries each and are not interpretable alone.
- `assoc-Self` has 0 real sites in all three repos (`Self::f()` never appears in code) and qualified-trait has 0: spec §25/§27 are covered only by synthetic tests.
- Only 2 real in-repo trait-dispatch entries exist (supplement, above): trait dispatch on real code is barely measured.
- External agreement partly comes from a name rule: a method whose receiver type is unknown and whose name no project symbol defines is classed external (`std-or-dependency`, probable). Agreements from that rule alone: dev 10 of 24, held-out 5 of 17.
- Dev tuning: resolver rules were developed while looking at dev failures (each with a synthetic test), so dev numbers are optimistic. The held-out column is the honest number.
- Cached RESOLVED edges are not re-resolved on warm rebuilds (shared indexer behaviour): an edit in another file can leave a stale or dangling edge until a cold rebuild. INDEX_VERSION only protects against old cache formats.
- In-repo blanket impls only make competing candidates ambiguous; their bounds are not checked.
- Macros are structural only: no expansion, and calls inside macro arguments are not extracted.
- No inference for closures, iterator adapters, `for`/`match`/`if let` patterns, `.await`, or external return types.
- A library imported by its own crate name (`use <crate>::...` from `tests/` or `src/bin/`) is not mapped to the local library (the import is marked external; crate identity needs Cargo.toml), so calls through it stay unresolved.
- Dev history, quoted from the task reports (earlier commits, same script, dev split): no resolver 0/21 recall_exact, 0/24 external; structural resolution (Task 7) 10/21, precision 10/10, external 11/24; typed receivers (Task 8) 20/21, 20/20, 24/24, FP 0/45.
- Parse slowdown of +65-69% from call extraction (see Performance).

## Analysis (written after the run, from the rows above)

**Held-out is worse than dev on recall.** recall_exact fell from 20/21 on dev to 8/12 on held-out. Precision stayed at 100% (8/8) and the false-positive rate at 0/29, so the misses are all conservative ones: the adapter left the edge unresolved and claimed no wrong target. All 4 held-out misses are in ripgrep-ignore (5/9 there), and all have the syntactic category `local-method`. The evidence for a real gap is borderline at these sizes. Held-out has 12 resolved labels. A Fisher exact test on 20/21 vs 8/12 gives p≈0.047; it is quoted only to show how thin the evidence is, and the size of the gap is not precise. The resolver was not tuned after the run: its behaviour is unchanged since `6ff9822`. The later performance fix left every edge byte-identical.

Why each held-out miss happened. I checked each one by hand against the checkout source and the adapter edges after the run, without changing any code:

| entry | root cause | auto attribution | what it really is |
|---|---|---|---|
| `walk.rs:2476` `builder.min_depth(..)` | `builder` is bound twice in the same test fn (`let builder = ...` then `let mut builder = ...`). The single-binding rule (Task 8: any second binding of the name in the fn makes the type unknown) refuses to type it. | IMPL_RESOLUTION | Known conservative limit (shadowing is not modelled flow-sensitively) |
| `dir.rs:537` `mat.is_ignore()` | `mat` is bound three times in `matched` (dir.rs:516, 527, 535), in sibling blocks. The same rule applies. | IMPL_RESOLUTION | Same limit |
| `dir.rs:1203` `td.path()` | `td = tmpdir()`. `tmpdir()` resolves exactly, but its return type `TempDir` comes from `use crate::{.., tests::TempDir}`, and `tests` is an inline `mod tests { }` inside lib.rs (lib.rs:490). Item paths into inline modules are not resolved (`TempDir::new()` at dir.rs:1141 gets `no-type:unknown-type`), so the receiver type is unknown. | IMPL_RESOLUTION | Really USE_RESOLUTION: the path goes through an inline module |
| `dir.rs:1537` `td.path()` | Same as dir.rs:1203. | IMPL_RESOLUTION | Really USE_RESOLUTION |

The deterministic attribution rule assigns every method-like miss to IMPL_RESOLUTION. For the two `td.path()` rows the root cause is actually use/module resolution. The rule was left unchanged, because the evaluation was frozen before the run.

The only dev miss (`mini-redis tests/client.rs:36` `client.set(..)`) is the crate-name import limit: the library is imported as `mini_redis::...`, which is not mapped to the local crate.

**No wrong edges to inspect.** Across all splits and both blocks there are 0 wrong exact and 0 wrong probable edges, and 0 UNKNOWN attributions. The plan asks for 5 or more inspected UNKNOWN or wrong-exact examples per repo, but none exist. Every failure (5 in total, all unresolved misses) is listed and explained above.

**External agreement** is 17/17 on held-out. 5 of those 17 come only from the name rule (dev: 10 of 24), so about a third of the "agreement" rests on a name heuristic, not on a known receiver type. Across whole repos, the name rule decides 142/865 (16.4%) of walkdir's non-macro edges, 315/946 (33.3%) of mini-redis's and 667/3158 (21.1%) of ripgrep-ignore's. These counts come from a full edge dump of each checkout, taken after the run.

**Trait dispatch.** Both real trait-dispatch entries (`walk.rs:1821`, `walk.rs:1837`, `Box<dyn ParallelVisitor>`) are in the held-out supplement. Both resolved correctly as `probable` trait declarations, which is why the supplement shows recall_exact 6/8 but recall_incl_probable 8/8. That is n=2.
