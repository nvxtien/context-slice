# v1.4 Phase 4 — JPA Entity Relationships and Spring Data Repository Semantics Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. **A task's brief is its own section plus this header (everything above `### Task 1`).**

**Goal:** Extract JPA entity relationship metadata (`@OneToMany`/`@ManyToOne`/`@ManyToMany`/`@OneToOne`, with explicit `mappedBy`/`@JoinColumn`/`fetch`/`cascade`) and Spring Data repository semantics (repository→entity linkage from `extends JpaRepository<Entity, Id>`-shaped interfaces, conservative derived-query-method-name hints, `@Query` text capture) — the fourth family built on the v1.4 architecture (Phase 0 scaffolding, Phase 1 routes, Phase 2 dependency injection, Phase 3 transactions, all already merged). This is the largest single-topic family so far, spanning spec §22-29, and reuses Phase 2's project-wide resolver-hook architecture (entity-type resolution needs the whole project's symbol set, exactly like bean identity did).

**Architecture:** Two extractor files, one per sub-concern (repository interfaces and entity classes are structurally different declarations, so — matching this codebase's established one-extractor-per-concept convention — they get separate files, not one merged file): `src/languages/java/enterprise/jpa-entity.ts` (entity relationship fields → `ENTITY_RELATION`) and `src/languages/java/enterprise/spring-data.ts` (repository role → `PERSISTS_ENTITY`, derived query methods + `@Query` → `REPOSITORY_QUERY`). Both need project-wide entity-type resolution (a relationship field's or a repository's generic type argument must resolve to the actual project entity class, unique-simple-name-match, conservative — exactly Phase 2's bean-identity rule), so both register a resolver via Phase 2's `registerEnterpriseResolver` hook (already generic and reusable, confirmed reusable by Phase 2's own final review) rather than building a second resolution mechanism. One composer, `composeJpaContext` in `src/planner/composition.ts`, surfaces all three relation kinds together (they're one coherent "how does this class persist" story for a developer, not three separate composition passes) — Java-only-gated, reusing the shared `"enterprise relation"` `CompositionReason` every prior family uses.

**Tech Stack:** TypeScript (ESM `.js` imports), `npx tsx --test`, existing `ProjectIndex`/`buildPreview`/`registerEnterpriseExtractor`/`registerEnterpriseResolver` (`src/languages/java/enterprise/registry.ts`, the resolver hook added by Phase 2).

**Spec:** `docs/prompt/CONTEXTSLICE_V1.4_JAVA_ENTERPRISE_CONTEXT_SEMANTICS.md` — §22 (repository type/entity/id/role), §23 (derived query methods, conservative structural hints only, no full parser without evidence), §24 (`@Query` text capture, link to repository method/entity, no JPQL/SQL execution), §25 (entity annotation recognition), §26 (entity relationship graph: owning field, relation kind, target type, mappedBy/join metadata, fetch/cascade only when explicit), §27 (preserve explicit fetch mode only, label framework defaults as defaults not source facts if ever reported), §28 (cascade metadata only when task-relevant, never flood context), §29 (persistence flow — reuse existing call graph + this phase's metadata, no new call-resolution logic, no claimed SQL), §44-47 (planner wiring, explainability, confidence, no annotation spam), §50-51 (per-family discipline, retention rule), §55-58 (mandatory metrics + this family's own `entity_relation_recall`/`repository_linkage_recall` pair, §58 failure attribution), §60-62 (no repo-specific hacks, no JDT, no Spring/JPA bootstrap — no Hibernate, no real query execution, no schema introspection), §63-64 (fixture corpus: JPA entity, one-to-many, many-to-one, repository interface, derived query, `@Query` — positive; ambiguous JPA relation target — negative, per spec's own named case), §3-4 (regression gates). ## Real-repository grounding (checked before writing this plan, not guessed)
`grep -rl "@Entity" benchmarks/checkouts/{spring-petclinic,petclinic-rest}/src/main/java` finds 14 entity classes total. `Owner.java` (spring-petclinic) has a real, representative case: `@Entity`, `@Table(name = "owners")`, and `@OneToMany(cascade = CascadeType.ALL, fetch = FetchType.EAGER)` `@JoinColumn(name = "owner_id")` `@OrderBy("name")` on `private final List<Pet> pets`. `grep -rln "extends.*Repository"` finds 10 repository interfaces across both repos, including the exact spec §22 example shape (`OwnerRepository extends JpaRepository<Owner, Integer>`) and a real multi-supertype case (`SpringDataUserRepository extends UserRepository, Repository<User, String>`, petclinic-rest). Derived query methods found in real source: `findById`, `findByLastName`, `findByLastNameStartingWith`, `findByName`, `findByPetId` — all single-property or simple structural shapes, no `And`/`Or` compound predicates observed. `@Query` is used in 3 files (e.g. `PetTypeRepository.findPetTypes()`: `@Query("SELECT ptype FROM PetType ptype ORDER BY ptype.name")`). This means: (a) entity relationship extraction (§25-26) and the repository→entity link (§22) are both real, evidenced work; (b) derived-query structural-hint parsing (§23) has real single-property evidence but no real compound (`And`/`Or`) case — implement it per spec (conservative hints only) but say in Task 5's report that compound predicates are validated by fixtures only; (c) `@Query` text capture (§24) has real evidence; (d) `mappedBy` (the inverse side of a bidirectional relationship) was NOT found in either repo's `@OneToMany`/`@ManyToOne` usage (both repos' relationships are unidirectional, using `@JoinColumn` instead) — implement `mappedBy` per spec since it's explicitly named, but say plainly in Task 5 that it's fixture-only, following the exact honesty discipline Phase 3 established for its own under-evidenced attributes.

## Global Constraints
- **Conservative entity-type resolution, reusing Phase 2's exact rule.** A relationship field's target type (unwrapped from `List<X>`/`Set<X>`/`Collection<X>` when a collection-typed relationship — `@OneToMany`/`@ManyToMany` are almost always collection-typed in real code, per this plan's own grounding; `@ManyToOne`/`@OneToOne` are almost always the bare type) or a repository's generic entity-type argument resolves to `exact` confidence ONLY when it matches exactly one project `class`/`interface` symbol by simple name; zero matches (a JDK/library type, or a not-yet-indexed entity in a different, unscanned part of the project) produces NO relation for that specific field/argument; multiple matches produce `unresolved`, `targetSymbolId` omitted, never a fabricated winner. This is IDENTICAL to Phase 2's `resolveBeanType` rule — reuse that function's logic (not necessarily its code, since it lives in `dependency-injection.ts` and each extractor stays self-contained per the established convention, but re-derive the SAME algorithm, don't invent a different one).
- **Reuse Phase 2's resolver-hook architecture.** Both `jpa-entity.ts` and `spring-data.ts` register via `registerEnterpriseResolver` (from `src/languages/java/enterprise/registry.ts`, added by Phase 2, confirmed generic/reusable by Phase 2's final review — `EnterpriseResolver = (relations, allSymbols) => relations`, chained with `reduce`). Emit provisional relations at per-file extraction time (raw type name captured, `confidence: "unresolved"` placeholder), resolve them in the registered resolver function once the full project symbol set is available — the exact two-phase shape Phase 2 established. Do NOT invent a second resolver-registration mechanism.
- **Explicit-only metadata (§26-28).** `fetch`, `cascade`, and `mappedBy` are included in a relation's `evidence` ONLY when explicitly written in source (e.g. `fetch = FetchType.EAGER`) — never inferred, never a reported "default" value. If this phase's own code ever needs to state that a value wasn't explicit, it must be labelled as a framework default, never presented as a source-explicit fact (§27's own instruction) — in practice this means: simply omit anything not explicitly present, don't compute or report defaults at all.
- **No JPQL/SQL execution or parsing beyond raw text capture (§24, §61-62).** `@Query`'s argument is captured verbatim as `evidence` text. Never parse it for referenced tables/columns, never validate it, never claim it will execute correctly. No Hibernate, no real database, no schema introspection anywhere.
- **Conservative derived-query parsing (§23).** Split only on the `findBy`/`existsBy`/`deleteBy`/`countBy` prefix and, within the remainder, only on TOP-LEVEL `And`/`Or` (a naive `CamelCase`-boundary split on `And`/`Or` substrings is NOT top-level-aware and WILL misfire on a property name that happens to contain those letters, e.g. `findByAndroidVersion` — guard against this: only split on `And`/`Or` when they sit as a whole "word" between two other recognizable property-name segments, i.e. surrounded by uppercase-letter boundaries on both sides, not merely a case-insensitive substring match). Do not attempt to resolve the parsed property names against entity fields (entity fields aren't indexed as symbols with enough fidelity for that yet) — record them as evidence text only, a conservative structural hint, exactly as §23 asks.
- **Framework-neutral core (§5).** No `if (annotation === "Entity")`/`if (annotation === "OneToMany")`-style conditionals in `src/planner/`, `src/workflow/`, `src/indexer/` outside the one Java-language gate in `composeJpaContext`. All JPA/Spring-Data-specific logic lives in the two new extractor files.
- **No repo-specific hacks (§60).** No hardcoded class/package names anywhere in `src/`.
- **Explainability (§45), no annotation spam (§44, §47).** `composeJpaContext` never dumps an entity's full relationship graph or a repository's full derived-query list when only one relation is relevant to the already-composed context — same "no spam" discipline every prior composer enforces.
- Numbers in reports come from real runs of scripts; never hand-edited. Failures/limitations are reported, not hidden.
- Commit messages: short, single-line, imperative, NO `Co-Authored-By`/author trailer (repo memory rule). Tests flat under `tests/`, run with `npx tsx --test`.
- Reuse the existing pinned repositories (`benchmarks/repositories.json`: `spring-petclinic`, `petclinic-rest`) — this plan's own grounding already confirms 14 entities and 10 repository interfaces there, ample for measurement.

## Review Focus
1. A collection-typed relationship field (`List<Pet>`, `Set<X>`) must have its element type correctly unwrapped before resolution — resolving `List` itself (which matches no project entity) instead of `Pet` would silently produce zero relations for the MOST common real-world shape this plan's own grounding found (`Owner.pets`).
2. A relationship field whose annotation carries NO explicit `fetch`/`cascade`/`mappedBy` must not have any of those three appear in `evidence` — an implementation that always emits all three (with an inferred/default value) would violate §27's most explicit instruction.
3. A repository interface extending a NON-generic or unrelated interface (e.g. a plain marker interface, or `Repository<User, String>` reached indirectly through another project interface as in the real `SpringDataUserRepository` case) must not crash or silently mis-extract — the entity/id type-argument regex must be scoped to the KNOWN base-repository names (`JpaRepository`/`CrudRepository`/`PagingAndSortingRepository`/`Repository`) actually followed by `<...>`, not any `extends` clause.
4. A derived query method name containing "And"/"Or" as part of a property name, not as a predicate conjunction (e.g. a hypothetical `findByAndroidVersion`) must not be mis-split — Global Constraint's own named risk.
5. An entity relationship whose target type matches ZERO project symbols (e.g. a JDK collection element that isn't actually meant as an entity, or a genuinely external type) must produce NO relation, matching Phase 2's own zero-match rule exactly — not `unresolved`.
6. A large entity class with many relationship fields, or a repository interface with many derived-query methods, must not have every one dumped into context when only one is relevant to what's already composed — the same "no spam" failure mode every prior composer must avoid, re-applied here since two new relation kinds are being surfaced through one new composer.

import assert from "node:assert/strict";
import test from "node:test";
import { parseJava } from "../src/parser/java-parser.js";
import { extractEnterpriseRelations, resolveEnterpriseRelations, __resetEnterpriseExtractorsForTests } from "../src/languages/java/enterprise/registry.js";
import "../src/languages/java/enterprise/jpa-entity.js"; // side-effect: registers extractor + resolver

function relationsFor(files: Record<string, string>) {
  const allSymbols = [];
  const perFile: { symbols: any[]; relations: any[] }[] = [];
  for (const [filePath, source] of Object.entries(files)) {
    const { symbols } = parseJava(filePath, source);
    allSymbols.push(...symbols);
    perFile.push({ symbols, relations: extractEnterpriseRelations(symbols, filePath, source) });
  }
  const provisional = perFile.flatMap((f) => f.relations);
  const resolved = resolveEnterpriseRelations(provisional, allSymbols);
  return { symbols: allSymbols, relations: resolved };
}

test("a collection-typed @OneToMany resolves its unwrapped element type", () => {
  const owner = `
@Entity
class Owner {
    @OneToMany(cascade = CascadeType.ALL, fetch = FetchType.EAGER)
    @JoinColumn(name = "owner_id")
    private final java.util.List<Pet> pets = new java.util.ArrayList<>();
}
`;
  const pet = `@Entity\nclass Pet {}`;
  const { symbols, relations } = relationsFor({ "src/main/java/Owner.java": owner, "src/main/java/Pet.java": pet });
  const ownerClass = symbols.find((s) => s.name === "Owner")!;
  const petClass = symbols.find((s) => s.name === "Pet")!;
  const rel = relations.find((r) => r.kind === "ENTITY_RELATION" && r.sourceSymbolId === ownerClass.id)!;
  assert.ok(rel, "expected an ENTITY_RELATION for Owner.pets");
  assert.equal(rel.targetSymbolId, petClass.id);
  assert.equal(rel.targetLabel, "Pet");
  assert.equal(rel.confidence, "exact");
  assert.match(rel.evidence.join(" "), /OneToMany.*pets/);
  assert.match(rel.evidence.join(" "), /fetch = FetchType.EAGER/);
  assert.match(rel.evidence.join(" "), /cascade = CascadeType.ALL/);
});

test("no explicit fetch/cascade/mappedBy means none appear in evidence", () => {
  const order = `@Entity\nclass Order {\n    @ManyToOne\n    private Customer customer;\n}`;
  const customer = `@Entity\nclass Customer {}`;
  const { relations } = relationsFor({ "src/main/java/Order.java": order, "src/main/java/Customer.java": customer });
  const rel = relations.find((r) => r.kind === "ENTITY_RELATION")!;
  const text = rel.evidence.join(" ");
  assert.ok(!text.includes("fetch"));
  assert.ok(!text.includes("cascade"));
  assert.ok(!text.includes("mappedBy"));
});

test("a bidirectional relationship's explicit mappedBy is captured", () => {
  const order = `@Entity\nclass Order {\n    @OneToMany(mappedBy = "order")\n    private java.util.List<OrderItem> items;\n}`;
  const item = `@Entity\nclass OrderItem {}`;
  const { relations } = relationsFor({ "src/main/java/Order.java": order, "src/main/java/OrderItem.java": item });
  const rel = relations.find((r) => r.kind === "ENTITY_RELATION")!;
  assert.match(rel.evidence.join(" "), /mappedBy = "order"/);
});

test("a relationship target matching zero project symbols produces no relation", () => {
  const order = `@Entity\nclass Order {\n    @ManyToOne\n    private java.math.BigDecimal total;\n}`;
  const { relations } = relationsFor({ "src/main/java/Order.java": order });
  assert.equal(relations.length, 0);
});

test("an ambiguous relationship target (two same-name entities) is unresolved, never guessed", () => {
  const order = `@Entity\nclass Order {\n    @ManyToOne\n    private Status status;\n}`;
  const statusA = `package a;\n@Entity\nclass Status {}`;
  const statusB = `package b;\n@Entity\nclass Status {}`;
  const { relations } = relationsFor({
    "src/main/java/Order.java": order,
    "src/main/java/a/Status.java": statusA,
    "src/main/java/b/Status.java": statusB,
  });
  const rel = relations.find((r) => r.kind === "ENTITY_RELATION")!;
  assert.equal(rel.confidence, "unresolved");
  assert.equal(rel.targetSymbolId, undefined);
});

test("@Entity inside a comment produces no relation", () => {
  const source = `class PlainUtil {\n    // example: @Entity\n    void helper() {}\n}`;
  const { relations } = relationsFor({ "src/main/java/PlainUtil.java": source });
  assert.equal(relations.length, 0);
});

import assert from "node:assert/strict";
import test from "node:test";
import { parseJava } from "../src/parser/java-parser.js";
import { extractEnterpriseRelations, resolveEnterpriseRelations, __resetEnterpriseExtractorsForTests } from "../src/languages/java/enterprise/registry.js";

function relationsFor(files: Record<string, string>) {
