# v1.4 Phase 2 — Dependency Injection Semantics Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. **A task's brief is its own section plus this header (everything above `### Task 1`).**

**Goal:** Extract Spring dependency-injection relations (constructor injection, field `@Autowired`/`@Inject`/`@Resource`, explicit setter injection) with conservative bean-identity resolution — a unique project class/interface match is `exact`, an ambiguous match with a static `@Qualifier` hint that disambiguates it is still `exact` with the qualifier named as evidence, a genuinely ambiguous or unresolvable match is never fabricated — surface them as one explainable, budget-bounded composition candidate, and measure whether this recovers required facts on real Spring repositories, the second family built on the v1.4 Phase 0/1 architecture.

**Architecture:** A new extractor `src/languages/java/enterprise/dependency-injection.ts` follows the exact pattern `spring-mvc.ts` (Phase 1) established: it re-derives raw parameter/field text from each already-parsed `SymbolRecord`'s own `.source` (constructors' raw parameter list, and — since Java fields are NOT indexed as `SymbolRecord`s, confirmed in Phase 1 — a regex scan of the enclosing class's own `.source` for `@Autowired`/`@Inject`/`@Resource`-annotated field/setter declarations), resolves each dependency's declared type against `index.symbols` filtered to `kind === "class" | "interface"` by exact simple-name match (Java has NO import tracking in this codebase — `javaAdapter.parse` hardcodes `imports: []`, confirmed — so simple-name matching across ALL project symbols is the only available signal, which is also exactly what spec §13's "type maps uniquely to a project class/interface" already asks for), and emits `INJECTS_DEPENDENCY` relations via `registerEnterpriseExtractor`. A new `composeDependencyContext` in `src/planner/composition.ts` (Java-only gate, same shape as `composeRouteContext`/`composeImportContext`) surfaces one compact line per relevant dependency edge, wired into `buildPreview` the same way. This phase deliberately does NOT implement any Spring container simulation, bean-name matching against `@Component("name")`/`@Service("name")` values, or full `@Qualifier` resolution beyond "does the qualifier string equal a candidate class's simple name" — per spec §13's "do not invent a bean winner" and §14's "do not implement full Spring container resolution."

**Tech Stack:** TypeScript (ESM `.js` imports), `npx tsx --test`, existing `ProjectIndex`/`buildPreview`/`registerEnterpriseExtractor` (`src/languages/java/enterprise/registry.ts`, from Phase 0), existing regex-based `parseJava` (`src/parser/java-parser.ts` — read-only reference for this phase; Phase 1 needed one shared-file fix, this phase should not assume it will and must investigate before touching it, see Global Constraints).

**Spec:** `docs/prompt/CONTEXTSLICE_V1.4_JAVA_ENTERPRISE_CONTEXT_SEMANTICS.md` — §12 (injection patterns: constructor/field/explicit-setter), §13 (bean identity, ambiguity preserved, no invented winner), §14 (`@Qualifier` as static disambiguating evidence only), §44-47 (planner wiring, explainability, confidence, no annotation spam — same constraints Phase 1 already satisfied for routes, reused here), §50-51 (per-family benchmark discipline, retention rule), §55-58 (mandatory metrics; this family reports no dedicated numbered metric of its own in §56's list — `route_linkage_recall/precision` is route-specific — so this phase reports the mandatory §55 metrics plus a DI-specific recall/precision pair named analogously, `dependency_linkage_recall`/`dependency_linkage_precision`, and the §58 failure-attribution categories `DI_RESOLUTION`/`ANNOTATION_EXTRACTION`/others as they apply), §60-62 (no repo-specific hacks, no JDT, no Spring bootstrap), §63-64 (fixture corpus: constructor injection, field injection, qualifier — positive; ambiguous bean — negative), §3-4 (regression gates). NOT in this phase (deferred per §50's per-family discipline, matching how Phase 1 deferred everything outside routes): §15-43 (transactions, async/events/scheduled, JPA/Spring Data, Kafka, config/properties, test linkage), §65-84 (v1.4-wide release work — README, docs, version bump, packaging).

## Global Constraints
- **Bean identity (§13).** A dependency's declared type resolves to `exact` confidence ONLY when it matches exactly one project symbol of `kind === "class"` or `kind === "interface"` by simple (unqualified) name — OR when it matches more than one such symbol AND a static `@Qualifier("...")` value on the SAME injection point equals exactly one of those candidates' simple names (case-sensitive), in which case it is still `exact` with the qualifier named in `evidence`. Any other multi-candidate case is `unresolved` — the relation is still emitted (for failure-attribution/metrics visibility, same as Phase 1's unresolved routes) but with NO `targetSymbolId` and NEVER surfaced by `composeDependencyContext` (mirrors Phase 1's rule: only non-`unresolved` relations become composition context). A declared type matching ZERO project symbols (e.g. `RestTemplate`, `ObjectMapper`, any JDK/library type) produces NO relation at all — it is not a project bean, not ambiguity, nothing to report. Never invent a bean winner under any circumstance (explicit spec instruction, repeated twice in §13).
- **No Spring container bootstrap, no bean-name (`@Component("name")`) matching (§13, §14, §61-62).** Only simple-name type matching and literal `@Qualifier`-value-equals-simple-name matching, both static text comparisons. Do not attempt to resolve a qualifier against a `@Component`/`@Service`/`@Repository` custom bean name — that requires cross-file bean-name indexing this phase does not build; if evidence from Task 4 shows this materially matters, report it as a finding for a later phase, do not build it speculatively now.
- **Constructor injection preferred (§12).** When a class has BOTH a constructor with typed parameters AND field-level `@Autowired`/`@Inject`/`@Resource` members, extract relations for BOTH (the extractor stays exhaustive and honest — it does not suppress real field-level facts) but the extractor's own code must attempt constructor-parameter extraction FIRST (ordering, not exclusion) and constructor-sourced relations get `sourceSymbolId` = the constructor `SymbolRecord`'s own id (more precise than the class), which naturally reads as the preferred, most specific evidence.
- **Java fields are not indexed as symbols (confirmed fact from Phase 1, re-verify at the start of Task 1 rather than assuming stale).** Field-injection relations therefore use the ENCLOSING CLASS symbol's id as `sourceSymbolId` (no field symbol exists to be more specific), and setter-injection relations use the SETTER METHOD symbol's id (setters ARE indexed as `method`-kind symbols).
- **Framework-neutral core (§5).** No `if (annotation === "Autowired")`-style conditionals in `src/planner/`, `src/workflow/`, `src/indexer/` outside the one new Java-language gate in `composeDependencyContext` (`if (target.language !== "java") return [];`, same pattern as `composeImportContext`/`composeRouteContext`). All Spring-specific logic lives in `src/languages/java/enterprise/dependency-injection.ts`.
- **No repo-specific hacks (§60).** No hardcoded class/package names anywhere in `src/` (fixture/test/benchmark files may name real repo classes freely).
- **Shared-file caution (learned from Phase 1).** This phase's extractor should not need to touch `src/parser/java-parser.ts` at all — everything it needs (constructor parameter text, class source for field-regex scanning) is already available from existing `SymbolRecord` fields. If Task 1's real-repository measurement (Task 4) surfaces a genuine shared-parser gap the way Phase 1's did, follow the SAME discipline Phase 1 established: investigate with a minimal repro before touching the shared file, keep the change as narrow as possible, add a regression test for both the fix and the specific failure mode that motivated it, run the FULL test suite (not just Java tests), and bump `INDEX_VERSION` in `src/storage/sqlite.ts` in the same commit if Java parse output changes (confirm the current value first — do not assume it is still `"1.10.0"`, Phase 1 may not be the last thing to have touched it).
- **Explainability (§45), no annotation spam (§44, §47).** Every `INJECTS_DEPENDENCY` composition candidate's `evidence` names the injection mechanism (constructor parameter / `@Autowired` field / explicit setter) and, when used, the `@Qualifier` value. `composeDependencyContext` never attaches every dependency of a class — only ones relevant to symbols already in the composed context (same discipline as `composeRouteContext`'s `relatedIds` gating), never a full dependency-graph dump.
- Numbers in reports come from real runs of scripts; never hand-edited. Failures/limitations are reported, not hidden.
- Commit messages: short, single-line, imperative, NO `Co-Authored-By`/author trailer (repo memory rule). Tests flat under `tests/`, run with `npx tsx --test`.
- Reuse the existing pinned repositories (`benchmarks/repositories.json`: `spring-petclinic`, `petclinic-rest`) — both already have visible constructor-injected services/repositories in their controllers and services (`petclinic-owner-*` tasks already target classes with injected `OwnerRepository`/`PetRepository`, etc.) — do not fetch new repositories unless Task 4 finds a real gap that requires them (document why before adding one).

## Review Focus
1. A field/parameter whose type name matches ZERO project symbols (an external library type like `RestTemplate`) must produce NO relation — not `unresolved`, nothing at all — so common framework/JDK dependencies never pollute the relation set or the failure-attribution counts.
2. A field/parameter whose type matches MULTIPLE project symbols (e.g. two classes named `Validator` in different packages) with NO `@Qualifier`, or a `@Qualifier` value that doesn't match any candidate's simple name, must resolve `unresolved` and never be composed into context — the "do not invent a bean winner" rule is the single most spec-repeated instruction in this family, so a failure here is a spec violation, not a style nit.
3. A class with BOTH constructor injection and field-level `@Autowired` (a realistic partial-refactor state) must produce relations for both, correctly attributed to their own source location (constructor id vs. class id) — not merged, not one silently dropped.
4. An `@Autowired` annotation on something that is NOT actually a field or setter declaration (e.g. inside a comment, or on a local variable inside a method body — which is legal Java for method-scoped beans in older Spring test code) must not produce a false relation; mirrors Phase 1's comment-false-positive discipline, now applied to a field-scanning regex instead of a whole-symbol-source scan.
5. A large class with many injected dependencies must not have every dependency dumped into context when only one dependency's own callee is in the composed set — `composeDependencyContext` must be scoped to relations relevant to what's already included, exactly like `composeRouteContext`'s scoping (Phase 1 Review Focus 4, re-applied here since it's a new composer with the same failure mode available).

import assert from "node:assert/strict";
import test from "node:test";
import { parseJava } from "../src/parser/java-parser.js";
import { extractEnterpriseRelations, __resetEnterpriseExtractorsForTests } from "../src/languages/java/enterprise/registry.js";
import "../src/languages/java/enterprise/dependency-injection.js"; // side-effect: registers the extractor

function relationsFor(source: string, filePath = "src/main/java/OrderService.java") {
  const { symbols } = parseJava(filePath, source);
  return { symbols, relations: extractEnterpriseRelations(symbols, filePath, source) };
}

test("constructor injection resolves a unique project type as exact", () => {
  const source = `
class OrderRepository {}
class OrderService {
    private final OrderRepository repo;
    OrderService(OrderRepository repo) { this.repo = repo; }
}
`;
  const { symbols, relations } = relationsFor(source);
  const ctor = symbols.find((s) => s.kind === "constructor")!;
  const repoType = symbols.find((s) => s.kind === "class" && s.name === "OrderRepository")!;
  const rel = relations.find((r) => r.kind === "INJECTS_DEPENDENCY" && r.sourceSymbolId === ctor.id)!;
  assert.ok(rel, "expected a constructor-injection relation");
  assert.equal(rel.targetLabel, "OrderRepository");
  assert.equal(rel.targetSymbolId, repoType.id);
  assert.equal(rel.confidence, "exact");
  assert.match(rel.evidence.join(" "), /constructor parameter/);
});

test("field injection resolves via the enclosing class, since fields aren't symbols", () => {
  const source = `
class PaymentGateway {}
class Checkout {
    @Autowired
    private PaymentGateway gateway;
}
`;
  const { symbols, relations } = relationsFor(source, "src/main/java/Checkout.java");
  const checkoutClass = symbols.find((s) => s.kind === "class" && s.name === "Checkout")!;
  const rel = relations.find((r) => r.kind === "INJECTS_DEPENDENCY" && r.sourceSymbolId === checkoutClass.id)!;
  assert.equal(rel.targetLabel, "PaymentGateway");
  assert.equal(rel.confidence, "exact");
  assert.match(rel.evidence.join(" "), /@Autowired field/);
});

test("explicit setter injection attributes to the setter method symbol", () => {
  const source = `
class Notifier {}
class Alerts {
    private Notifier notifier;
    @Autowired
    void setNotifier(Notifier notifier) { this.notifier = notifier; }
}
`;
  const { symbols, relations } = relationsFor(source, "src/main/java/Alerts.java");
  const setter = symbols.find((s) => s.kind === "method" && s.name === "setNotifier")!;
  const rel = relations.find((r) => r.kind === "INJECTS_DEPENDENCY" && r.sourceSymbolId === setter.id)!;
  assert.equal(rel.targetLabel, "Notifier");
  assert.equal(rel.confidence, "exact");
  assert.match(rel.evidence.join(" "), /setter/);
});

test("a type matching zero project symbols produces no relation", () => {
  const source = `
class Checkout {
    @Autowired
    private RestTemplate client;
}
`;
  const { relations } = relationsFor(source, "src/main/java/Checkout.java");
  assert.equal(relations.length, 0);
});

test("an ambiguous type with no qualifier is unresolved, never guessed", () => {
  const source = `
class Validator {}
class Checkout {
    private final Validator v;
    Checkout(Validator v) { this.v = v; }
}
`;
  // A second, differently-scoped Validator to force real ambiguity across the file set —
  // simulate via a second file's symbols merged in, since parseJava is per-file: build the
  // relations call with a combined symbol list from two separate parses.
  const first = parseJava("src/main/java/other/Validator.java", "package other;\nclass Validator {}");
  const { symbols: checkoutSymbols } = parseJava("src/main/java/Checkout.java", source);
  const allSymbols = [...first.symbols, ...checkoutSymbols];
  const relations = extractEnterpriseRelations(allSymbols, "src/main/java/Checkout.java", source);
  const ctor = checkoutSymbols.find((s) => s.kind === "constructor")!;
  const rel = relations.find((r) => r.sourceSymbolId === ctor.id)!;
  assert.equal(rel.confidence, "unresolved");
  assert.equal(rel.targetSymbolId, undefined);
});

test("a static @Qualifier resolves ambiguity to the matching candidate", () => {
  const first = parseJava("src/main/java/other/Validator.java", "package other;\nclass Validator {}");
  const source = `
class Validator {}
class Checkout {
    Checkout(@Qualifier("Validator") Validator v) {}
}
`;
  const { symbols: checkoutSymbols } = parseJava("src/main/java/Checkout.java", source);
  const allSymbols = [...first.symbols, ...checkoutSymbols];
  const relations = extractEnterpriseRelations(allSymbols, "src/main/java/Checkout.java", source);
  const ctor = checkoutSymbols.find((s) => s.kind === "constructor")!;
  const local = checkoutSymbols.find((s) => s.kind === "class" && s.name === "Validator")!;
  const rel = relations.find((r) => r.sourceSymbolId === ctor.id)!;
  assert.equal(rel.confidence, "exact");
  assert.equal(rel.targetSymbolId, local.id);
  assert.match(rel.evidence.join(" "), /@Qualifier/);
});

test("both constructor and field injection on the same class produce distinct relations", () => {
  const source = `
class Repo {}
class Gateway {}
class Service {
    private final Repo repo;
    @Autowired
    private Gateway gateway;
    Service(Repo repo) { this.repo = repo; }
}
`;
  const { symbols, relations } = relationsFor(source, "src/main/java/Service.java");
  const ctor = symbols.find((s) => s.kind === "constructor")!;
  const cls = symbols.find((s) => s.kind === "class" && s.name === "Service")!;
  assert.ok(relations.find((r) => r.sourceSymbolId === ctor.id && r.targetLabel === "Repo"));
  assert.ok(relations.find((r) => r.sourceSymbolId === cls.id && r.targetLabel === "Gateway"));
});

test("@Autowired inside a comment produces no relation", () => {
  const source = `
class Widget {}
class Screen {
    // example: @Autowired
    private Widget widget;
}
`;
  const { relations } = relationsFor(source, "src/main/java/Screen.java");
  assert.equal(relations.length, 0);
});
