# v1.4 Phase 3 → Phase 4 Recommendation

**Source:** `benchmarks/results/v1.4-phase3-transactions.{md,json}`, `tests/java-enterprise-transaction-fixtures.test.ts`, the ledger at this plan's (now-deleted) SDD workspace.

## What was measured

Spring `@Transactional` boundary metadata: explicit attribute values only (`readOnly`, `propagation`, `isolation`, `rollbackFor`, `noRollbackFor`, `timeout`), surfaced as one compact composition line whenever the annotated method is already in the composed context. A bare `@Transactional` produces no relation — the existing rendered skeleton already shows the bare annotation name, so this family's whole value is closing the ONE real gap: attribute values were previously invisible everywhere.

- **Fixture corpus:** 6 cases (bare `@Transactional`, `readOnly=true`, multiple attributes together, a self-invocation case honestly labelled as testing plumbing rather than call-graph-aware behavior — this family deliberately has none, per §17's "never claim proxy interception" being satisfied structurally by never inspecting call relationships at all — and a comment false-positive), indexed through the real `ProjectIndex`, all correctly classified.
- **Real-repository measurement** (spring-petclinic, petclinic-rest — reused existing pinned repos): an independent oracle found `transaction_boundary_recall = 100.0%`, `transaction_boundary_precision = 100.0%` (21/21 explicit-attribute entries matched, 0 false positives) — **with zero extractor changes needed**, the cleanest of all three v1.4 families measured so far (Phase 1 needed 2 fix rounds closing real bugs; Phase 2 needed 1; this phase needed none).
- **A real correction to this plan's OWN grounding section**, found during Task 4 and independently re-verified by review: the plan claimed spring-petclinic has zero `@Transactional` usage. It actually has 2 — `VetRepository.java`'s two abstract interface methods (`findAll()`, `findAll(Pageable)`), both `@Transactional(readOnly = true)`. The plan's headline totals (41 total, 21 explicit, all `readOnly=true`) were still correct; only the per-repo attribution prose was wrong. This also proved, as a side effect, that the extractor correctly handles body-less interface method declarations (no `{`) — a shape none of Task 1's own unit tests happened to exercise.
- **Honest scope, stated in three places (grounding section, Task 4's report, this document):** only `readOnly` has real-repository evidence. `propagation`, `isolation`, `rollbackFor`, `noRollbackFor`, `timeout`, and the §17 self-invocation caution are validated by the fixture corpus alone — neither pinned repository uses them.
- **Regression:** `npm run benchmark` (fixed after Phase 2 to be a self-contained fixture smoke test again) produced byte-for-byte identical output before and after this phase's changes. `npm test` 381/381 green throughout (up from 362 baseline at the start of this plan).

## §51 retention rule — does transaction-boundary composition earn its place?

- **Recovers required facts:** yes, on real evidence, for `readOnly`. 21/21 real occurrences correctly extracted and composed with zero false positives.
- **False positives:** 0, across both the real-repository run and the fixture corpus, including the body-less-method case the real repositories surfaced that no unit test anticipated.
- **Context cost:** one line, `// Transaction\n<method> (<attributes>)`, budget-bounded through the same shared composition allowance every other family's composer already uses, never surfaced for a bare `@Transactional` (avoiding redundant spam with the existing skeleton's own `ANNOTATIONS` line).
- **Verdict: keep, with the same "proven narrower than the full spec" caveat Phase 2 carried.** `readOnly` is solidly evidenced. The other five attributes and the self-invocation caution are implemented correctly per the fixture corpus but unproven by real-world occurrence — not a reason to revert anything, simply an honest limit on what this phase's numbers can claim.

## Real findings beyond the family itself

1. **A plan-authoring error, not an implementation error** — this plan's own real-repository grounding section undercounted spring-petclinic's `@Transactional` usage (2 real occurrences missed, likely because the original grep that informed this plan was scoped to `service`/`controller`-shaped files and missed a `repository`-package interface). Found and corrected by Task 4's own independent measurement discipline, the same self-checking process that caught Phase 2's own test-6 plan defect.
2. **Zero shared-file changes needed.** Unlike Phase 1 (`java-parser.ts` methodRe fix) and Phase 2 (the same file, plus a new resolver-hook architecture), this phase touched only its own new file, `composition.ts`, `preview.ts`, and one `index.ts` import line — the smallest footprint of the three families.
3. **`npm run benchmark`** (fixed as a separate follow-up before this phase started) continues to work correctly — this phase's Task 4 re-confirmed it byte-for-byte stable, closing the loop on that earlier finding.

## Ranked recommendation for the next family (v1.4 Phase 4)

**Spring Data / JPA (spec §22-29) is the clearly best-grounded next family**, based on fresh evidence gathered while writing this recommendation (not reused from an earlier phase's numbers):

`grep -rhoE "@Async|@EventListener|ApplicationEventPublisher|@Scheduled|@KafkaListener|@Entity|@OneToMany|@ManyToOne|@ManyToMany|@OneToOne|extends\s+(Jpa|Crud|Paging)Repository" benchmarks/checkouts/{spring-petclinic,petclinic-rest}/src/main/java` finds:

| Signal | Count |
|---|---:|
| `@Entity` | 14 |
| `@OneToMany` | 5 |
| `@ManyToOne` | 5 |
| `@ManyToMany` | 2 |
| `extends JpaRepository` | 2 |
| `@Async` / `@EventListener` / `ApplicationEventPublisher` / `@Scheduled` / `@KafkaListener` | **0** |

Async/events/scheduled/Kafka remain at zero across every check this session has run against these two repositories (first checked before Phase 3 began, re-confirmed here) — they would still force either new pinned repositories or a vacuous real-repository measurement, the same reasoning Phase 2's recommendation used to rule them out in favor of `@Transactional`. JPA/entity relationships, by contrast, have real, substantial signal (14 entities, 12 relationship annotations, 2 Spring Data repository interfaces) — enough for a real `ENTITY_RELATION`/`PERSISTS_ENTITY`/`REPOSITORY_QUERY` extraction family (spec §22-29) to be measured meaningfully on the currently-pinned repositories without adding new ones.

This is a recommendation per §50's per-family discipline, not a commitment — Phase 4 should re-derive its own scope from a fresh read of §22-29 rather than assume this document's framing is exhaustive, the same caveat every prior phase's recommendation has carried forward.

## What Phase 3 deliberately did not do

Per the plan's own Spec line and §50's per-family discipline: no async/events/scheduled, Spring Data/JPA, Kafka, config/properties, or test-linkage extraction; no propagation-semantics simulation (explicitly forbidden by §15); no bean-name or call-graph-aware analysis of any kind (this family's entire design deliberately avoids it, both because nothing in §15-17 asks for it and because it's the structural mechanism that satisfies §17 without any risk of a wrong claim); no README/docs/version bump/packaging work (still v1.4-wide release items per §75-77, deferred exactly as Phase 0, 1, and 2 all deferred them).
