# v1.4 Phase 3 — @Transactional Boundary Semantics Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. **A task's brief is its own section plus this header (everything above `### Task 1`).**

**Goal:** Extract Spring `@Transactional` boundary metadata — explicit attribute values only (`readOnly`, `propagation`, `isolation`, `rollbackFor`, `noRollbackFor`, `timeout`) — and surface them as one explainable composition line whenever the annotated method is already in the composed context, closing the one real gap this family has: the existing rendered skeleton already shows a bare `@Transactional` name for any included caller/callee, but never its attribute values. The third family built on the v1.4 architecture (Phase 0 scaffolding, Phase 1 routes, Phase 2 dependency injection, all already merged).

**Architecture:** A new extractor `src/languages/java/enterprise/transactions.ts` follows Phase 1's simpler, single-file pattern (NOT Phase 2's project-wide resolver — a transaction boundary is a fact about the annotated method alone, resolvable entirely within one file, no cross-file bean identity involved): for each `method`-kind `SymbolRecord`, regex the method's own `.source` prefix (the same technique `spring-mvc.ts` uses for its mapping annotations) for `@Transactional`/`@Transactional(...)`, parse any explicit attribute list, and emit a `TRANSACTION_BOUNDARY` relation only when at least one explicit attribute is present (a bare `@Transactional` needs no relation — the existing `renderSkeleton()`'s `ANNOTATIONS` section, unchanged since before this phase, already shows the bare annotation name in every caller/callee skeleton). `composeTransactionContext` in `src/planner/composition.ts` (Java-only-gated, reusing the shared `"enterprise relation"` `CompositionReason` Phase 1 and Phase 2 both already use) surfaces one compact attribute-summary line when the target itself, or an already-included caller/callee, carries such a relation.

**Tech Stack:** TypeScript (ESM `.js` imports), `npx tsx --test`, existing `ProjectIndex`/`buildPreview`/`registerEnterpriseExtractor` (`src/languages/java/enterprise/registry.ts`, unchanged since Phase 0 — this family does NOT need Phase 2's resolver-hook addition, `registerEnterpriseResolver`, since nothing here needs project-wide symbol visibility).

**Spec:** `docs/prompt/CONTEXTSLICE_V1.4_JAVA_ENTERPRISE_CONTEXT_SEMANTICS.md` — §15 (extract transaction boundaries, include metadata only when task-relevant, do not simulate propagation semantics), §16 (preserve explicit attribute values only, never dump full annotation text unnecessarily), §17 (never claim self-invocation triggers Spring proxy interception — document the limitation), §44-47 (planner wiring, explainability, confidence, no annotation spam — same constraints Phase 1/2 already satisfied, reused here), §50-51 (per-family benchmark discipline, retention rule), §55-58 (mandatory metrics; §56 has no `@Transactional`-specific metric name, so this phase reports the mandatory §55 metrics plus its own `transaction_boundary_recall`/`precision` pair, named analogously to Phase 1/2's own family-specific pairs), §60-62 (no repo-specific hacks, no JDT, no Spring bootstrap), §63-64 (fixture corpus: transactional method, transaction annotation attributes — positive; self-invoked transactional method — negative, per spec's own named negative case list), §3-4 (regression gates). NOT in this phase (deferred per §50's per-family discipline): §18-43 (async/events/scheduled, Spring Data/JPA, Kafka, config/properties, test linkage), §65-84 (v1.4-wide release work).

## Real-repository grounding (checked before writing this plan, not guessed)
`grep -rn "@Transactional" benchmarks/checkouts/{spring-petclinic,petclinic-rest}/src/main/java` finds 41 occurrences (0 in spring-petclinic's own controllers/services — all 41 are in petclinic-rest's `service`/`repository`/`rest/controller` packages). Of those 41, exactly 21 carry an explicit attribute, and **every single one of the 21 is `@Transactional(readOnly = true)`** — `grep -rhoE "@Transactional\([^)]*\)" ... | sort -u` returns only that one distinct attribute expression across both repositories. Neither `propagation`, `isolation`, `rollbackFor`, `noRollbackFor`, nor `timeout` appears anywhere in either pinned repository. No self-invocation pattern (`this.someTransactionalMethod()`) was found in `ClinicServiceImpl.java`, the file with the most `@Transactional` methods. This means: (a) `readOnly` extraction is real, evidenced, in-scope work; (b) the other five attribute kinds must still be IMPLEMENTED (the spec names all six, and a fixture corpus can exercise them even where the real repos don't), but Task 4's real-repository measurement will only be able to evidence `readOnly` — say so honestly in that task's report, don't imply broader real-world validation than the repos provide; (c) the self-invocation caution (§17) has no real-repository positive case to measure either — it is validated entirely by fixture/unit tests in this plan, and Task 4 should say so plainly rather than searching for a case that isn't there.

## Global Constraints
- **Attribute-only extraction (§16).** A relation is emitted ONLY when at least one of `readOnly`, `propagation`, `isolation`, `rollbackFor`, `noRollbackFor`, `timeout` is explicitly present in the annotation's argument list. A bare `@Transactional` (no parentheses, or empty parentheses) produces NO relation — the existing `SymbolRecord.annotations` array (bare name list) and `renderSkeleton()`'s `ANNOTATIONS` section already surface it, so a relation here would be redundant "annotation spam" the spec explicitly forbids (§44, §47).
- **No propagation simulation (§15).** Never compute or claim actual runtime propagation behavior (e.g. "this call starts a new transaction," "this call joins the caller's transaction"). Only report the STATIC PRESENCE of explicit attribute values as written in source.
- **Self-invocation caution (§17), stated as code and tested, not just prose.** The extractor and composer must never emit evidence implying that a call from one method to another method of the SAME class (`this.x()` or an implicit unqualified call resolved to a sibling method) triggers Spring's proxy-based transactional behavior. Structural call evidence (the call itself, already surfaced generically by existing call resolution — untouched by this phase) stays; this phase's OWN evidence strings must never claim proxy interception across a self-invocation. Add an explicit fixture/test proving this (see Review Focus and Task 3).
- **Framework-neutral core (§5).** No `if (annotation === "Transactional")`-style conditionals in `src/planner/`, `src/workflow/`, `src/indexer/` outside the one Java-language gate in `composeTransactionContext` (`if (target.language !== "java") return [];`, the same pattern `composeRouteContext`/`composeDependencyContext` already use). All Spring-specific logic lives in `src/languages/java/enterprise/transactions.ts`.
- **No resolver-hook reuse without cause.** This family's extraction is entirely per-file (a method's own `@Transactional` is a fact about that method alone) — do NOT register a `registerEnterpriseResolver` for this family. If, unexpectedly, a real need for project-wide resolution emerges while implementing, STOP and treat that as a real, surprising finding to report — the plan's own grounding says it shouldn't be needed.
- **No repo-specific hacks (§60).** No hardcoded class/package names anywhere in `src/` (fixture/test/benchmark files may name real repo classes freely).
- **Explainability (§45), no annotation spam (§44, §47).** Every composed candidate's `evidence` names the exact attribute(s) found, verbatim as written in source (e.g. `readOnly = true`). `composeTransactionContext` never attaches a transaction-boundary line for a method whose ONLY annotation is a bare `@Transactional` (nothing to add beyond what the skeleton already shows), and never for a method not already in the composed context.
- Numbers in reports come from real runs of scripts; never hand-edited. Failures/limitations are reported, not hidden.
- Commit messages: short, single-line, imperative, NO `Co-Authored-By`/author trailer (repo memory rule). Tests flat under `tests/`, run with `npx tsx --test`.
- Reuse the existing pinned repositories (`benchmarks/repositories.json`: `spring-petclinic`, `petclinic-rest`) — do not fetch new repositories; the real-repository grounding above already confirms `petclinic-rest` alone provides 41 real `@Transactional` occurrences, ample for measurement.

## Review Focus
1. A bare `@Transactional` (no parentheses) must produce NO relation at all — Global Constraint's own "attribute-only extraction" rule; a wrong implementation here would either miss real attribute cases or spam every transactional method regardless of attributes.
2. `@Transactional(readOnly = true)` must extract `readOnly: true` correctly; `@Transactional()`  (empty parens) must behave identically to a bare `@Transactional` (no relation) — an easy off-by-one in "does this annotation have parens" vs. "does it have a non-empty argument list."
3. A method that calls another method of the SAME class, where the callee is `@Transactional`, must never produce composed evidence implying the self-invocation itself is transactionally significant — the exact §17 caution, and the one most likely to produce a subtly wrong/misleading explanation if missed.
4. Multiple attributes in one annotation (e.g. a hypothetical `@Transactional(readOnly = true, timeout = 30)` — not present in the real repos, but the spec names all six attributes and a fixture must exercise more than one at once) must all be captured and rendered together, not just the first one matched.
5. A large service class with many `@Transactional` methods must not have every one dumped into context when only one method (or its caller/callee) is actually in the composed slice — same "no spam" discipline Phase 1 (routes) and Phase 2 (DI) both already enforce for their own composers, re-applied here since this is a new composer with the same failure mode available.

import assert from "node:assert/strict";
import test from "node:test";
import { parseJava } from "../src/parser/java-parser.js";
import { extractEnterpriseRelations, __resetEnterpriseExtractorsForTests } from "../src/languages/java/enterprise/registry.js";
import "../src/languages/java/enterprise/transactions.js"; // side-effect: registers the extractor

function relationsFor(source: string, filePath = "src/main/java/PaymentService.java") {
  const { symbols } = parseJava(filePath, source);
  return { symbols, relations: extractEnterpriseRelations(symbols, filePath, source) };
}

test("a bare @Transactional produces no relation", () => {
  const source = `
class PaymentService {
    @Transactional
    void charge(String id) {}
}
`;
  const { relations } = relationsFor(source);
  assert.equal(relations.length, 0);
});

test("empty-parens @Transactional() behaves the same as bare", () => {
  const source = `
class PaymentService {
    @Transactional()
    void charge(String id) {}
}
`;
  const { relations } = relationsFor(source);
  assert.equal(relations.length, 0);
});

test("readOnly = true is extracted with exact confidence", () => {
  const source = `
class ClinicService {
    @Transactional(readOnly = true)
    Owner findOwner(long id) { return null; }
}
`;
  const { symbols, relations } = relationsFor(source, "src/main/java/ClinicService.java");
  const method = symbols.find((s) => s.name === "findOwner")!;
  const rel = relations.find((r) => r.kind === "TRANSACTION_BOUNDARY" && r.sourceSymbolId === method.id)!;
  assert.ok(rel, "expected a TRANSACTION_BOUNDARY relation");
  assert.equal(rel.confidence, "exact");
  assert.equal(rel.targetLabel, "readOnly=true");
  assert.deepEqual(rel.evidence, ["readOnly = true"]);
});

test("multiple explicit attributes are all captured together", () => {
  const source = `
class OrderService {
    @Transactional(readOnly = false, timeout = 30, propagation = Propagation.REQUIRES_NEW)
    void place(String id) {}
}
`;
  const { symbols, relations } = relationsFor(source, "src/main/java/OrderService.java");
  const method = symbols.find((s) => s.name === "place")!;
  const rel = relations.find((r) => r.sourceSymbolId === method.id)!;
  assert.equal(rel.evidence.length, 3);
  assert.ok(rel.evidence.some((e) => e.includes("readOnly")));
  assert.ok(rel.evidence.some((e) => e.includes("timeout")));
  assert.ok(rel.evidence.some((e) => e.includes("propagation")));
});

test("rollbackFor and noRollbackFor are both recognized", () => {
  const source = `
class RiskyService {
    @Transactional(rollbackFor = IllegalStateException.class, noRollbackFor = ValidationException.class)
    void run() {}
}
`;
  const { symbols, relations } = relationsFor(source, "src/main/java/RiskyService.java");
  const method = symbols.find((s) => s.name === "run")!;
  const rel = relations.find((r) => r.sourceSymbolId === method.id)!;
  assert.equal(rel.evidence.length, 2);
});

test("isolation is recognized", () => {
  const source = `
class LedgerService {
    @Transactional(isolation = Isolation.SERIALIZABLE)
    void post() {}
}
`;
  const { symbols, relations } = relationsFor(source, "src/main/java/LedgerService.java");
  const method = symbols.find((s) => s.name === "post")!;
  const rel = relations.find((r) => r.sourceSymbolId === method.id)!;
  assert.equal(rel.evidence.length, 1);
  assert.match(rel.evidence[0], /isolation/);
});

test("@Transactional inside a comment produces no relation", () => {
  const source = `
class PlainUtil {
    // example: @Transactional(readOnly = true)
    void helper() {}
}
`;
  const { relations } = relationsFor(source, "src/main/java/PlainUtil.java");
  assert.equal(relations.length, 0);
});
