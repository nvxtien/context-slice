# v1.5 Phase 1 — Real-Repository Evaluation of Rust use/module/re-export Resolution

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (or executing-plans). Single task; steps use checkbox syntax.

**Goal:** Measure how well the merged Phase 1 Rust adapter (module paths, `use`/`crate`/`self`/`super` resolution, `pub use` re-exports) actually works on three real, pinned open-source Rust repositories — with independent oracles, failure attribution, and honest reporting — WITHOUT changing any production code.

**Architecture:** A pinned-repository manifest (`benchmarks/rust-repositories.json`, same shape as `benchmarks/python-repositories.json`) feeds the existing `benchmarks/fetch-checkouts.ts`. A new script `benchmarks/v1.5-rust-real-repositories.ts` builds a `ProjectIndex` per checkout and computes the spec §72 resolution metrics plus a failure-attribution breakdown, then writes `benchmarks/results/v1.5-phase1-rust-real-repositories.{md,json}`. The script is measurement-only: production code (`src/`) is not modified, and no measured behavior may be tuned to look better. Real defects found are REPORTED (with evidence), not fixed here.

**Spec:** `docs/prompt/CONTEXTSLICE_V1.5_RUST_SUPPORT.md` — §67-68 (real pinned repos, diversity), §70 (independent ground truth, no leakage), §72 (`module_resolution_rate`, `use_resolution_rate`, `reexport_resolution_rate`), §74 (failure attribution categories), §80 (cold-index performance, partial). Semantic call recall/precision, retrieval/required-fact recall, and context-reduction metrics are OUT OF SCOPE: they need Rust call resolution (Phase 2) and hand-written task ground truth (later).

## Global Constraints

- Do NOT modify anything under `src/`. If a defect is found, document it in the report; do not fix it in this task.
- Do NOT read or reuse resolver internals as the oracle. `resolveRustModule`/`rustModuleIndex`/`modulePathFor` must not be used to verify their own output — oracles must be independent (filesystem layout, raw source text, tree-sitter, or index data that the resolver did not produce).
- No benchmark leakage: nothing under `src/` may reference repository names, expected counts, or expected results.
- Pinned commits are exact and must be used verbatim (below). `benchmarks/checkouts/` is git-ignored — never commit checkouts.
- Commit messages: short, single-line, imperative, NO `Co-Authored-By` or author trailer.
- New TS files use `.js`-suffixed relative imports (ESM), run via `tsx`.
- Report numbers must come from a real run of the script. Never hand-edit numbers.

Key invariant: `ImportRecord.module` is everything EXCEPT the final imported-name segment (e.g. `use crate::a::B;` → module `crate::a`, importedName `B`; `use serde::Serialize;` → module `serde`).

- [ ] **Step 2: Manifest + wiring.** Create `benchmarks/rust-repositories.json` with the three entries from the table above; add its path to `manifests` in `benchmarks/fetch-checkouts.ts`; add the npm script. Run `npm run benchmark:checkouts` and confirm the three checkouts appear under `benchmarks/checkouts/` at the pinned commits and that Python/TS/Java checkouts are unaffected (the script must still pass for them).

- [ ] **Step 3: Write the failing oracle tests first (TDD).** In `tests/rust-real-repositories-oracle.test.ts`, test the pure oracle helpers below against tiny synthetic temp directories. Each helper is INDEPENDENT of `src/languages/rust/resolve.ts`:

  1. `expectedModuleFile(declaringFile, modName, fileExists)` — the Rust filesystem rule for `mod foo;` declared in file `X`: let `dir` = `dirname(X)` if `basename(X)` is `mod.rs`, `lib.rs`, or `main.rs`; otherwise `dir` = `dirname(X)/<stem of X>`. The expected file is the first existing of `dir/foo.rs`, `dir/foo/mod.rs`; else `undefined`. (Also honor an explicit `#[path = "..."]` attribute by treating such declarations as `skipped-path-attribute`, not as failures.)
  2. `classifyUse(importRecord)` — `"anchored"` if `module.split("::")[0]` is `crate`/`self`/`super` (or `module` is exactly one of them); else `"non-anchored"`.
  3. `targetContainsName(index, resolvedFile, importedName)` — true when `resolvedFile` declares a symbol named `importedName`, OR has an `ExportRecord` with `exportedName === importedName`, OR has a `mod` symbol named `importedName` (importing a submodule), OR the imported name is a variant/associated item that cannot be checked (return `"unverifiable"` for names starting with an uppercase letter that match an `enum` symbol's variants only if you can determine that from source text; otherwise just `false`). Keep this deliberately simple and label it a PROXY for precision, not ground truth.
  Write tests that fail first (helpers don't exist), then implement, then pass.

- [ ] **Step 4: Implement the evaluation script.** For each pinned repo, build `new ProjectIndex(<checkout dir>)`, call `.rebuild()` once cold (record `elapsedMs`, `filesParsed`, `parseErrors`) and once warm (second `.rebuild()`; verify the resolved values are IDENTICAL between cold and warm — report any difference as a defect), then compute:

  - **Coverage:** number of `.rs` files indexed, symbols, imports, exports, files with `parseError`.
  - **`module_resolution_rate`** (spec §72): build an INDEPENDENT oracle of each file's true module path by walking the declaration chain: treat as crate roots every file that is `lib.rs`/`main.rs` directly inside a `src/` directory, plus each `src/bin/*.rs` and each top-level `tests/*.rs` and `build.rs` (each is its own crate root with module path `[]`), plus any other file that has no parent declaration (report those as `orphan`). From each root, follow every file-backed `mod foo;` declaration using `expectedModuleFile` (helper 1) to build `oracleModulePath(file)` = declaring file's path + `[foo]`. Then for every file reached this way compare `oracleModulePath(file)` with the implementation under test, `modulePathFor(file)` (imported from `src/languages/rust/parse.ts` — here it is the SUBJECT being checked, never the oracle). Report per repo: `files_reached`, `agree`, `disagree` (with examples and a reason: e.g. `src/bin/*.rs` and `tests/*.rs` are their own crate roots but `modulePathFor` maps them to `["bin","x"]`/`["tests","x"]` — attribute these as `RUST_STATIC_LIMIT`/`CARGO_WORKSPACE_RESOLUTION` per the rules, don't hide them), `orphans`, `declarations_total`, `declarations_file_missing` (with reasons: `#[path]`, `#[cfg]`-gated, generated), `skipped-path-attribute`.
  - **`use_resolution_rate`** (spec §72): split every `ImportRecord` into `anchored` vs `non-anchored`. For anchored: `resolved` (has `resolvedFile`), `unresolved`. For non-anchored: `external` (has `externalPackage`), `local-resolved` (has `resolvedFile`), `neither`. Also the precision PROXY: among resolved imports that have an `importedName` and are not wildcards, the fraction where `targetContainsName` is true; list a bounded sample (≤10 per repo) of resolved-but-name-missing cases with file:line for manual inspection. Report wildcard imports separately (count, resolved count).
  - **`reexport_resolution_rate`** (spec §72): over `ExportRecord`s: with `resolvedFile`; non-wildcard ones with `symbolId`; wildcard ones with `resolvedFile`.
  - **Failure attribution (spec §74 categories)** for every anchored-unresolved import, every `mod foo;` whose oracle file is missing from the index, and every resolved-but-name-missing sample: assign exactly ONE of `MODULE_RESOLUTION`, `USE_RESOLUTION`, `CARGO_WORKSPACE_RESOLUTION`, `MACRO_EXPANSION_LIMIT`, `RUST_STATIC_LIMIT`, `PARSER`, `UNKNOWN` by DETERMINISTIC RULES you write down in the report (e.g. import file has `parseError` → `PARSER`; import in `src/bin/*` naming the package's own lib crate → `CARGO_WORKSPACE_RESOLUTION`; target is a `#[path]`/`#[cfg]`/inline-`mod`/macro-generated item → `RUST_STATIC_LIMIT` or `MACRO_EXPANSION_LIMIT`; otherwise `UNKNOWN`). Report counts per category per repo. `UNKNOWN` must be reported honestly, not minimized; inspect ≥5 `UNKNOWN` examples per repo by reading the source and state what they really are.
  - **Performance:** cold and warm `rebuild()` ms per repo.

  Write results as JSON (all raw numbers, the rule table, and bounded example lists) and as Markdown (tables + a plain-language "Findings" section). The Markdown MUST include: a benchmark-scope statement (repos, pins, sparse scope, what is NOT measured: call resolution, retrieval/required-fact recall, context reduction, hand-written tasks), the rule table for attribution, and a "Defects and limitations found" section listing each real defect with evidence (file:line examples) — distinguishing (a) production defects, (b) known documented limitations (workspace/bin/inline-mod/`#[path]`), (c) oracle limitations.
