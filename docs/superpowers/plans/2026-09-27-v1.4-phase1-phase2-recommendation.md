# v1.4 Phase 1 → Phase 2 Recommendation

**Source:** `benchmarks/results/v1.4-phase1-spring-mvc-routes.{md,json}`, `benchmarks/java-enterprise-route-oracle.{spring-petclinic,petclinic-rest}.json`, `tests/java-enterprise-*.test.ts`, `tests/fixtures/java-enterprise/`.

## What was measured

Spring MVC route semantics (`ROUTE_TO_HANDLER` relations: composed HTTP method + path → handler method), surfaced as one explainable, budget-bounded composition candidate when a task's context includes a route handler or its direct caller/callee.

- **Fixture corpus:** 6 cases (class+method literal composition, method-only route, two overloaded handlers, dynamic/unresolved class path, same-class constant resolution, comment false-positive), indexed through the real `ProjectIndex`, all correctly classified.
- **Real-repository measurement** (spring-petclinic, petclinic-rest — reused existing pinned repos, no new fetches): an independent oracle (18 hand-spot-checked route entries, zero imports from `src/`) found `route_linkage_recall = 100.0%`, `route_linkage_precision = 100.0%`, 0 false positives — after one bounded fix round for 2 concrete extraction bugs the first measurement (83.3% recall) surfaced.
- **Regression:** `npm test` 335/335 green throughout (up from 315 baseline at the start of this plan). The intended `npm run benchmark` regression-gate script was found pre-existing broken on `main` itself (schema drift, unrelated to this phase) — spun off as its own follow-up task rather than fixed here or used as this phase's signal.

## §51 retention rule — does Spring MVC route composition earn its place?

- **Recovers required facts:** yes. The real gap this phase closes is genuine: a route handler's full path (class-level prefix + method-level suffix) lives on two different symbols, and the class-level one is not otherwise surfaced in composed context (the enclosing-type skeleton's `declarationLine()` only takes the first source line, which for an annotated class is the first annotation, not the class declaration itself — a pre-existing, unrelated bug, not touched here). The one existing pinned repository with a real class+method composition (`PetController`) is spot-checked and correct.
- **False positives:** 0 across 18 real-repository route entries and 6 fixtures. Confidence rules held conservative throughout — no `exact` was ever produced from a non-literal expression; the extraction bugs found were recall misses (real routes not surfaced), never fabricated ones.
- **Context cost:** one compact `// Route\n<METHOD> <path> → <handler>` line, budget-bounded through the same `compositionAllowance` share as every other composer, never a class/module dump.
- **Verdict: keep.** Both retention-rule conditions (recovers facts, no unacceptable false positives) are met with real evidence, not synthetic fixtures alone.

## Real findings beyond the family itself

Two things this phase's benchmark-first discipline (spec §1) surfaced that were not about routes specifically:

1. **A real, shared-code bug**: `src/parser/java-parser.ts`'s `methodRe` did not handle an annotation interleaved between modifiers and return type (`public @ResponseBody Vets foo()`) — a real Spring pattern (`VetController.showResourcesVetList`), not a route-specific edge case. Fixed narrowly (one new optional regex group, byte-identical group 1/2 behavior, hand-traced and reviewed for backward compatibility), with `INDEX_VERSION` correctly bumped (1.9.0 → 1.10.0) since this is the first Java parse-output change since that versioning scheme existed.
2. **`npm run benchmark` is broken on `main`**, independent of this phase (schema drift between `benchmark.ts`'s flat `fact.patterns` and `tasks.json`'s nested `verification.patterns`). Flagged to the user as a separate follow-up task (not fixed in this plan, to keep this phase's diff scoped to Spring MVC).

## Ranked recommendation for the next family (v1.4 Phase 2)

Per spec §12-14, dependency injection is the natural next family:

- **Already grounded in this phase's own fixtures and real repos.** `OrderController`'s field-injected `OrderService` (this phase's own Task 2 fixture) and every pinned petclinic controller already have constructor/field-injected services — no new repository or fixture category needed to start.
- **Directly composable with route context.** A route composition candidate today shows "POST /orders/{id} → OrderController.update"; the natural next fact a developer needs is "and `update` is backed by `OrderService`, injected via constructor" — the same explainability discipline (§45), same conservative confidence rules (§46), same Java-only composer-gate pattern (`composeImportContext`/`composeRouteContext` precedent) apply directly.
- **Lower extraction risk than the alternatives.** Transactions/async/events (§15-21) require attribute-level annotation parsing (isolation level, propagation) with more edge cases; Spring Data/JPA (§22-29) needs entity relationship graph construction; Kafka (§30+) needs cross-file topic-string matching. DI is comparatively a single, well-bounded correlation (constructor parameter / field type → bean type), consistent with how narrowly-scoped Phase 1 turned out to be tractable.

This is a recommendation per §50's per-family discipline, not a commitment — Phase 2 should re-derive its own scope from a fresh read of §12-14 rather than assume this document's framing is exhaustive.

## What Phase 1 deliberately did not do

Per the plan's own Spec line and §50's per-family discipline: no dependency injection, transactions, async/events, Spring Data/JPA, Kafka, config/properties, or test-linkage extraction; no README/`docs/rust-support.md`-equivalent Java doc; no `package.json` version bump (v1.4 has never been version-bumped — Phase 0 correctly deferred this too, and it remains a v1.4-wide release item per §75-77, not per-family work); no packaging/clean-room smoke test extension (§73-74, also v1.4-wide). These stay open until v1.4's remaining families are measured.
