# Java Parser: Multi-Line Annotation Arguments and Comment-Text False Positives Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. **A task's brief is its own section plus this header (everything above `### Task 1`).**

**Goal:** Fix two real, independently-diagnosed bugs in the shared `src/parser/java-parser.ts` regex-based Java parser, both found (and correctly deferred, not fixed) during v1.4 Phase 4's real-repository measurement: (1) a multi-line annotation argument list (e.g. a `@Query(\n  value = "...",\n  countQuery = "...")` spanning several lines, a real, common Spring Data pattern) causes the ENTIRE leading-annotation match to fail, so the affected symbol's `.source`/`.annotations` silently start AFTER both annotations, losing them completely; (2) `interface`/`class`/`enum`/`record` keyword-matching is not comment-aware, so javadoc prose containing one of those words followed by a lowercase word (e.g. `"...so this interface can easily be extended..."`) produces a bogus symbol (confirmed: a fake `interface:can` symbol in `spring-petclinic`'s `OwnerRepository.java`/`VetRepository.java`). Root-caused with direct reproduction against real checked-out source (not guessed) before this plan was written.

**Architecture:** Bug (1) is a narrow regex fix — four occurrences of the pattern `\([^\n]*\)` (bounding an annotation's argument text to a single line) become `\([^)]*\)` (bounded by the next closing paren instead, allowing embedded newlines) in `typeRe`, `constructorRe`, `methodRe`'s own group 1, and the `METHOD_EXTRA_PREFIX_ITEM` constant methodRe's group 3 reuses. Bug (2) needs a new capability the parser doesn't have at all: a comment-aware scan. A new `stripComments(source)` helper blanks the CONTENTS of every `//` line comment and `/* ... */` block comment (replacing non-newline characters with spaces, preserving every character's original offset and every newline, and correctly skipping over string/char literals so a comment marker embedded in a string — e.g. `"http://..."` — is never mistaken for a real comment start) into a same-length "codeOnly" string; `typeRe`, `methodRe`, and `constructorRe` all scan THIS blanked string to decide where symbols start and end, while every `.source`/`.body`/`range()` slice continues to read from the ORIGINAL, un-blanked `source` at the same offsets — so real code (including any comment text legitimately inside a symbol's own body) is indexed verbatim, only the SCANNING decisions change.

**Tech Stack:** TypeScript (ESM `.js` imports), `npx tsx --test`, the existing regex-based `src/parser/java-parser.ts` (no tree-sitter, no compiler — matches this file's own established approach).

**Spec:** No v1.4 spec section names this directly — these are correctness fixes to the shared Java structural parser all v1.4 Java-enterprise families depend on (§5 "Tree-sitter first"/structural-analysis-only still applies: no compiler, no javac, pure text/regex fixes matching the file's existing style). Both bugs were found and documented as deferred findings in `benchmarks/results/v1.4-phase4-jpa-spring-data.md` (Task 5's real-repository measurement), which this plan's own investigation re-confirmed and root-caused precisely before writing any fix.

## Real-repository grounding (checked before writing this plan, not guessed)
Both bugs were reproduced directly against `benchmarks/checkouts/petclinic-rest` and `benchmarks/checkouts/spring-petclinic` before this plan was written:
- Bug 1: `SpringDataOwnerRepository.java`'s `findAll(Pageable)` method (lines 48-52: `@Override` then a THREE-LINE `@Query(\n  value = "...",\n  countQuery = "...")`) — confirmed via a direct `parseJava` call that the resulting `findAll` symbol's `.source` is exactly `"Page<Owner> findAll(Pageable pageable);"` (no leading annotations at all) and `.annotations` is `[]`. The exact same shape exists for `Pet.findAll(Pageable)` in `SpringDataPetRepository.java` (Task 5's report already named both).
- Bug 2: `OwnerRepository.java`'s javadoc (line 28: `"... so this interface can easily be extended for Spring Data ..."`) — confirmed via a direct `parseJava` call that the symbol list includes a spurious `{ kind: "interface", name: "can" }` alongside the real `OwnerRepository` interface. `VetRepository.java` has the identical javadoc sentence and the identical bogus symbol (Task 5's report already named both files).
- `grep -c '\[\^\\n\]\*'` / manual read of `src/parser/java-parser.ts` confirms exactly 4 occurrences of the newline-excluding annotation-argument pattern (`typeRe` line ~12, `METHOD_EXTRA_PREFIX_ITEM` line ~25, `methodRe`'s own group 1 line ~27, `constructorRe`'s equivalent group) and confirms NO existing comment-stripping mechanism exists anywhere in this file (every per-family enterprise extractor — `spring-mvc.ts`, `dependency-injection.ts`, `transactions.ts`, `jpa-entity.ts`, `spring-data.ts` — independently re-derives its OWN local, `//`-only, single-symbol-scoped comment guard; none of them touch or could fix the shared parser's OWN top-level `class`/`interface`/`enum`/`record`/method/constructor keyword matching, which is what bug 2 needs).

## Review Focus
1. A multi-line annotation whose argument list itself contains a `)` inside a string literal (e.g. `@Query("SELECT o FROM Owner o WHERE o.name = ')'")`) must not have the regex's new `[^)]*` bound stop early at the string's own literal `)` — check whether this is a REAL risk introduced by the fix (the original `[^\n]*` had the exact same "stops at first literal char that looks like a delimiter, doesn't understand strings" limitation, just for newlines instead of parens — confirm whether this is a genuine regression or an equally-pre-existing, orthogonal limitation not made worse by this specific fix).
2. A `//` inside a string literal (e.g. `String url = "http://example.com";`) must not be treated as the start of a line comment by the new `stripComments` helper — this is the single most likely real-world false positive for a naive comment stripper, and Java source is full of URLs in string literals (log messages, annotation values, javadoc `@see` links).
3. A `/*` or `*/`-shaped substring inside a STRING literal (rarer, but possible: `"/* not a comment */"`) must not confuse the block-comment scanner.
4. A symbol whose own body legitimately contains comment syntax (e.g. a method containing `// a real inline comment` or a field with a Javadoc-style `/** ... */` immediately above it that IS meant to be part of that symbol's indexed context) must still have that comment text preserved verbatim in `.source`/`.body` — the blanking must only affect the SCANNING regex, never the sliced output.
5. Running the fix against the ORIGINAL confirmed real-repository symptom files (`OwnerRepository.java`, `VetRepository.java`, `SpringDataOwnerRepository.java`, `SpringDataPetRepository.java`) must show BOTH bugs are gone and no other symbol in those same files regresses (e.g. the real `OwnerRepository`/`VetRepository` interface symbols themselves must still be found correctly, not accidentally suppressed by the new comment-awareness).

### Task 2: Fix comment-text false positives in type/method/constructor detection

**Files:**
- Modify: `src/parser/java-parser.ts` (new `stripComments` helper; wire it into the `typeRe`, `methodRe`, `constructorRe` scan loops)
- Test: `tests/parser-comment-stripping.test.ts` (new)

**Interfaces:**
- Consumes: nothing new.
- Produces: a new, NOT exported (internal to this file, matching the file's existing convention of keeping its helper functions module-private) function `stripComments(source: string): string` returning a SAME-LENGTH string where every `//`-to-end-of-line comment and every `/* ... */` block comment has its content (not its delimiters — replace the WHOLE matched comment span, delimiters included, to be safe and simple) replaced with spaces, all newlines preserved exactly (so line/column math elsewhere in the file, which depends on counting newlines via `point()`, is completely unaffected), and all string/char literal content left untouched (scanned over, not modified, and never misinterpreted as containing a comment start). `typeRe.exec`/`matchAll`, `methodRe.matchAll`, and `constructorRe.matchAll` all run against this blanked string INSTEAD of `source` for the purpose of finding match positions (`match.index`, `match[0].length`, etc.) — every place the code currently does `source.slice(...)` to build `.source`/`.body`/`range()` continues to slice from the ORIGINAL `source` at the SAME offsets the blanked-string match produced (since `stripComments` is guaranteed same-length/same-offsets, no coordinate translation is needed).

- [ ] **Step 1: Write the failing test first** (`tests/parser-comment-stripping.test.ts`):

```ts
import assert from "node:assert/strict";
import test from "node:test";
import { parseJava } from "../src/parser/java-parser.js";

test("a keyword-shaped word inside a block-comment javadoc does not become a fake symbol", () => {
  const source = [
    "/**",
    " * conventions so this interface can easily be extended for Spring Data",
    " */",
    "public interface OwnerRepository {",
    "    Owner findById(Integer id);",
    "}",
  ].join("\n");
  const { symbols } = parseJava("OwnerRepository.java", source);
  const names = symbols.filter((s) => s.kind === "interface").map((s) => s.name);
  assert.deepEqual(names, ["OwnerRepository"], "the javadoc's 'interface can' must not produce a fake symbol");
});

test("a keyword-shaped word inside a line comment does not become a fake symbol", () => {
  const source = "// this class can be extended\nclass Real {}";
  const { symbols } = parseJava("Real.java", source);
  const names = symbols.filter((s) => s.kind === "class").map((s) => s.name);
  assert.deepEqual(names, ["Real"]);
});

test("a // inside a string literal is not treated as a comment start", () => {
  const source = 'class X {\n    String url = "http://example.com/interface can";\n}';
  const { symbols } = parseJava("X.java", source);
  // The real class X must still be found, and no fake "can" interface/class symbol
  // must appear even though the string literal contains comment-marker-shaped text
  // and the word "interface"/"class"-adjacent text.
  assert.ok(symbols.some((s) => s.kind === "class" && s.name === "X"));
  assert.ok(!symbols.some((s) => s.name === "can"));
});

test("a /* inside a string literal does not start a false block comment", () => {
  const source = 'class X {\n    String s = "/* not a comment */";\n    void real() {}\n}';
  const { symbols } = parseJava("X.java", source);
  assert.ok(symbols.some((s) => s.kind === "method" && s.name === "real"), "the real method after the tricky string must still parse");
});

test("a real comment legitimately inside a symbol's own source is preserved verbatim", () => {
  const source = [
    "class X {",
    "    // a real inline comment explaining y",
    "    void y() { /* also real */ }",
    "}",
  ].join("\n");
  const { symbols } = parseJava("X.java", source);
  const y = symbols.find((s) => s.kind === "method" && s.name === "y")!;
  assert.match(y.source, /a real inline comment explaining y/);
  assert.match(y.body ?? "", /also real/);
});
```
