# v1.4 Phase 2 → Phase 3 Recommendation

**Source:** `benchmarks/results/v1.4-phase2-dependency-injection.{md,json}`, `benchmarks/results/java-enterprise-di-oracle.{spring-petclinic,petclinic-rest}.json`, `tests/java-enterprise-di-fixtures.test.ts`, the ledger at this plan's (now-deleted) SDD workspace.

## What was measured

Spring dependency-injection semantics: constructor injection (gated on a Spring stereotype annotation or `@Autowired`/`@Inject` on the constructor itself — a plain, unmanaged class's constructor is never mistaken for DI), field injection (`@Autowired`/`@Inject`/`@Resource`), and explicit setter injection, with conservative bean identity (a unique project class/interface match by simple name is `exact`; zero matches produce no relation at all; ambiguous matches are `unresolved`, never fabricated even when a `@Qualifier` is present, since candidates are found BY simple name and a qualifier equal to that same simple name can never break the tie — real bean-name-based disambiguation would need cross-file `@Component("name")` indexing this phase deliberately did not build).

- **Fixture corpus:** 5 cases (constructor injection, field injection, a qualifier case whose evidence is captured but correctly never resolves ambiguity, a genuine ambiguous-bean negative case, a comment false-positive), indexed through the real `ProjectIndex`, all correctly classified.
- **Real-repository measurement** (spring-petclinic, petclinic-rest — reused existing pinned repos): an independent oracle found `dependency_linkage_recall = 100.0%`, `dependency_linkage_precision = 100.0%`, 0 false positives — reached with **zero product-code changes** after Task 1's own two fix rounds (which happened before this measurement ran) had already closed the real gaps. The one real issue this task's own process found was in its *evaluation harness* (an initial scope mismatch comparing `src/main/java`-only oracle entries against product relations that also included legitimate `src/test/java` injections), not in the extractor.
- **Honest caveat, stated plainly in the committed report per this phase's own fix round:** the sample is overwhelmingly constructor injection (34 of 35 unique-bean oracle entries). Field injection contributes exactly 1 entry, setter injection contributes 0 matched entries (its one oracle entry is an external framework type, correctly excluded). The 100% constructor-injection result is well-evidenced; the field/setter 100% is not — it simply hasn't been meaningfully exercised by these two repositories.
- **Regression:** `npm test` 363/363 green throughout (up from 338 baseline at the start of this plan). `npm run benchmark`'s pre-existing brokenness (found at the end of Phase 1, spun off as its own follow-up) had still not landed by the time this phase's Task 4 ran — `npm test` was used as the fallback signal again, per the same precedent Phase 1 established.

## §51 retention rule — does dependency-injection composition earn its place?

- **Recovers required facts:** yes, on the evidence available. Constructor-injection edges are real, correctly gated, and correctly resolved on both pinned repositories with no false positives. Whether field/setter injection recovers real facts in practice is not yet evidenced — not refuted, just untested by this evidence set.
- **False positives:** 0 across 35 real-repository unique-bean entries (all mechanisms) and the fixture corpus. The conservative-resolution discipline (no invented bean winners, ever) held throughout, including through a genuine plan-defect discovery during Task 1's review (a self-contradictory test scenario for `@Qualifier` disambiguation, correctly identified and fixed rather than forced to pass).
- **Context cost:** one compact `// Dependency\n<Class>.<field> → <Type> (<mechanism>)` line, budget-bounded through the same shared `compositionAllowance` as every other composer (routes, imports, enclosing-type skeleton), never a full dependency-graph dump — the "no annotation spam" gate (only surfaces a dependency when something using it is already in the composed context) held in both the fixture tests and the real-repo run.
- **Verdict: keep constructor injection; field/setter injection is unproven, not disproven.** A future evaluation on a repository with heavier field-injection usage (many older or test-style Spring codebases favor field injection over constructor injection) would give this a fairer test. Not a reason to revert anything now — the mechanism is implemented correctly per the fixture corpus, it's simply under-exercised by the two currently-pinned repositories.

## Real findings beyond the family itself

1. **A genuine architectural gap in the v1.4 Phase 0 extractor model**, found and resolved by Task 1: the per-file `EnterpriseExtractor` signature cannot see other files' symbols, but bean-identity resolution needs the whole project's symbol set. Task 1 added a generic, framework-neutral resolver-hook mechanism to the shared registry (`registerEnterpriseResolver`/`resolveEnterpriseRelations`), run once after the per-file parse loop completes — mirroring the codebase's existing call-resolution post-pass pattern. This is reusable machinery: any future family whose relations need project-wide (not just per-file) resolution can register its own resolver the same way, without touching `src/indexer/index.ts` again.
2. **A real, narrow `parseJava` quirk** (not fixed, worked around): an `@Autowired`-annotated constructor is parsed twice by the shared regex-based parser (one copy with annotations captured, one without). The extractor deduplicates locally and — independently verified during review — does so safely regardless of which duplicate happens to survive, because the gating regex re-derives from `.source` text that's identical across both duplicates. Left as a documented, low-priority item for a future targeted `java-parser.ts` fix, following the same shared-file caution this plan's Global Constraints called for.
3. **A real plan defect**, found by the implementer and confirmed by two independent reviews: this plan's own Task 1 test scenario for `@Qualifier` disambiguation was mathematically incoherent (two same-simple-name candidates can never be distinguished by a qualifier value equal to that shared simple name). Corrected in-flight rather than forced to pass — a controller-authored defect, not an implementer shortfall, recorded here so it doesn't get miscredited.
4. **`npm run benchmark` is still broken on `main`**, independent of both this phase and Phase 1 (the follow-up task spun off after Phase 1 had not landed by the time this phase ran either). Still not fixed here, to keep this phase's diff scoped to dependency injection, same as Phase 1's own choice.

## Ranked recommendation for the next family (v1.4 Phase 3)

**Transactions (`@Transactional`, spec §15-17) is the clearly best-grounded next family**, based on real evidence gathered while writing this recommendation:

- `grep -rhoE "@Transactional|@Async|@EventListener|@Scheduled|@KafkaListener" benchmarks/checkouts/{spring-petclinic,petclinic-rest}/src/main/java` found **41 `@Transactional` occurrences and zero of every other async/event/scheduled/Kafka annotation**, across both pinned repositories. This is not a guess — it's a direct count against the exact real-repository evidence this phase's own process already fetched.
- This makes Kafka (§30+), scheduled work (§21), and event publishing (§19-20) poor near-term choices — the currently-pinned repositories cannot provide any real-repository evidence for them at all, which would force Phase 3 to either add new pinned repositories (a real cost, and a deviation from the "reuse existing repos" discipline both Phase 1 and Phase 2 followed) or ship a family whose real-world measurement is vacuous.
- `@Transactional` is also architecturally a smaller, more contained extraction problem than DI turned out to be: no project-wide resolution pass is needed (a transaction boundary is a fact about the annotated method itself, resolvable per-file, closer to Phase 1's route extraction than Phase 2's DI extraction), so it does not need to reuse or extend the new resolver-hook machinery Task 1 built — though that machinery remains available if a later family does need it.
- Composability with existing composers is natural: a route composition candidate already shows "POST /orders/{id} → OrderController.update"; a transaction-boundary candidate would naturally extend that same explainability chain ("...and `update` runs inside a transaction, isolation X, propagation Y") using the identical Java-only composer-gate pattern (`composeRouteContext`/`composeDependencyContext` precedent) and the identical conservative-confidence discipline (§46).

This is a recommendation per §50's per-family discipline, not a commitment — Phase 3 should re-derive its own scope from a fresh read of §15-17 rather than assume this document's framing is exhaustive, the same caveat Phase 1's recommendation carried forward correctly to this phase.

## What Phase 2 deliberately did not do

Per the plan's own Spec line and §50's per-family discipline: no transactions, async/events/scheduled, Spring Data/JPA, Kafka, config/properties, or test-linkage extraction; no bean-name (`@Component("name")`) indexing (explicitly excluded by this phase's own Global Constraints, and the root cause of why `@Qualifier` cannot yet meaningfully disambiguate); no generic-wrapper (`List<X>`/`Optional<X>`) unwrapping (documented, deliberately deferred, confirmed not exercised by either pinned repository); no `java-parser.ts` fix for the duplicate-constructor quirk (worked around locally, left for a future targeted fix); no README/docs/version bump/packaging work (still v1.4-wide release items per §75-77, deferred exactly as Phase 0 and Phase 1 both deferred them).
