# v1.4 Phase 1 — Spring MVC Route Semantics Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. **A task's brief is its own section plus this header (everything above `### Task 1`).**

**Goal:** Extract Spring MVC route semantics (`ROUTE_TO_HANDLER` relations: HTTP method + composed path → handler method), surface them as one explainable, budget-bounded composition candidate when a task's context includes a route handler, and measure whether this recovers required facts on real Spring MVC repositories — the first real family to populate the v1.4 Phase 0 architecture.

**Architecture:** A new extractor `src/languages/java/enterprise/spring-mvc.ts` re-scans each Java file's raw source (independently of the shared, name-only `SymbolRecord.annotations`) for `@RequestMapping`/`@GetMapping`/`@PostMapping`/`@PutMapping`/`@DeleteMapping`/`@PatchMapping` on classes and methods, correlates each annotation to its nearest already-parsed class/method `SymbolRecord` by source position, composes the full route (class-level path + method-level path) when both are string literals or same-class `static final String` constants, and emits `ROUTE_TO_HANDLER` relations via `registerEnterpriseExtractor` (Phase 0's registry). A new `composeRouteContext` in `src/planner/composition.ts` (Java-only gate, mirroring Rust's `composeImportContext`'s language gate) turns a target's or a related symbol's `ROUTE_TO_HANDLER` relation into one compact `CompositionCandidate` (`reason: "enterprise relation"`, already declared unused since Phase 0), wired into `buildPreview` the same way `composeImportContext` is. Controller→service→repository flow (spec §11) is NOT separately implemented — it already exists via the current call graph's direct-callee composition; this phase only adds the route fact itself, per the retention rule (§51: a rule stays only if it recovers a required fact no existing path already covers).

**Tech Stack:** TypeScript (ESM `.js` imports), `npx tsx --test`, existing `ProjectIndex`/`buildPreview`/`registerEnterpriseExtractor` (`src/languages/java/enterprise/registry.ts`), existing regex-based `parseJava` (`src/parser/java-parser.ts` — no tree-sitter query changes, no compiler dependency).

**Spec:** `docs/prompt/CONTEXTSLICE_V1.4_JAVA_ENTERPRISE_CONTEXT_SEMANTICS.md` — §8 (annotation extraction, route-relevant subset only), §9-11 (route semantics, composition, controller→service flow), §44-47 (planner wiring, explainability, confidence, no annotation spam), §50-51 (per-family benchmark discipline, retention rule), §55-58 (mandatory + route-specific metrics, failure attribution), §60-62 (no repo-specific hacks, no JDT, no Spring bootstrap), §63-64 (fixture corpus — route-relevant subset), §3-4 (regression gates). NOT in this phase (deferred to later v1.4 phases per §50's family-by-family discipline): §12-43 (DI, transactions, async/events, JPA/Spring Data, Kafka, config/properties, test linkage), §65-84 (large-class test, budget sweep beyond this family, full 18-24 task benchmark, packaging, README, docs, version bump, release blockers — these apply to v1.4 as a whole, not to a single family phase, matching how v1.4 Phase 0 itself deferred them).

## Global Constraints
- **Regression gates (§3-4), verified by replay, not re-derived.** Java retrieval recall = 100%, Java required-fact recall = 100%, Java semantic call regression = none, TypeScript retrieval recall/required-fact recall/semantic call recall/semantic call precision = 100%. Run `npm run benchmark:v04` (or whatever script currently reproduces these — confirm via `package.json`) before and after this phase's changes.
- **Framework-neutral core (§5).** No `if (annotation === "Transactional")`-style conditionals in `src/planner/`, `src/workflow/`, `src/indexer/` outside the one new Java-language gate (`if (target.language !== "java") return [];`, the same pattern `composeImportContext` already uses for Rust). All Spring-specific logic lives in `src/languages/java/enterprise/spring-mvc.ts`.
- **Conservative confidence (§10, §46).** `exact` only when both class-level and method-level paths are resolvable to literal strings (or a same-class `static final String` constant whose initializer is a literal); `probable` when only the method-level path is exact but the class-level prefix could not be verified never to exist, OR either constant resolves through one same-class hop; `unresolved`-confidence relations (raw, non-literal expression) are still recorded (evidence retained) but MUST NOT be surfaced as composition context — only `exact`/`probable` routes are shown to a developer, per §57 (a false exact edge is worse than an unresolved one) and §47 (no annotation spam). Never simulate Spring's runtime path-matching, property placeholders (`${...}`), or `PathPattern` semantics.
- **No repo-specific hacks (§60).** No `if (className === "OwnerController")`, no hard-coded package/topic/path strings anywhere in `src/`.
- **No JDT/LSP/compiler dependency (§61-62).** No Spring container bootstrap, no `javac`/JDT, no execution of project code. Pure regex/text analysis over already-parsed `SymbolRecord`s and raw file text, exactly like the existing Java parser.
- **Explainability (§45).** Every route composition candidate's `evidence` array must name which annotation(s) on which symbol(s) produced it, in plain text a developer can verify against the source.
- **No annotation spam (§44, §47).** Do not globally attach every annotation as context. Only a target/related symbol that is itself a route handler (has a `ROUTE_TO_HANDLER` relation as its source) gets a route composition candidate — never one for every method in a controller.
- Numbers in reports come from real runs of scripts; never hand-edited. Failures/limitations are reported, not hidden.
- Commit messages: short, single-line, imperative, NO `Co-Authored-By`/author trailer (repo memory rule). Tests flat under `tests/`, run with `npx tsx --test`.
- Reuse the existing pinned repositories (`benchmarks/repositories.json`: `spring-petclinic`, `petclinic-rest`) and existing tasks/manual-context files where they already target route handlers — do not fetch new repositories for this phase (§52's "at least three repositories" and 18-24 tasks are the FINAL v1.4 target across all families, not a per-phase requirement; §50 explicitly calls for per-family measurement first).

## Review Focus
1. A route annotation with a non-literal, non-resolvable path expression (e.g. `@RequestMapping(SOME_CONST_FROM_ANOTHER_CLASS)` or a method call) must never produce an `exact` relation and must never be surfaced as composition context — it must be recorded `unresolved` and silently excluded from `composeRouteContext`'s output, not shown with a wrong or guessed path.
2. A controller class with NO class-level `@RequestMapping` (route is method-level only, e.g. a plain `@GetMapping("/health")` with no enclosing prefix) must still produce a correct route (no leading `null`/`undefined` concatenation artifact).
3. Two methods in the same class annotated with the same HTTP-method mapping but different paths (e.g. overloaded `update` — real Java allows this) must each get their OWN correctly-attributed relation, not cross-contaminate via naive "first match wins" correlation.
4. A large controller class (many handler methods) must not have every method's route dumped into context when only one method is the task target — `composeRouteContext` must be scoped to the target/related symbols actually being composed, not the whole class.
5. Multiple negative fixtures (§64: dynamic route expression, self-invoked transactional-style call is not this family's concern but "route on a non-controller class" is) must not produce false relations — a `@RequestMapping`-shaped annotation on something that isn't actually a class/method symbol (e.g. inside a comment or a string literal) must not be picked up.

test("composes class-level and method-level literal paths into one exact route", () => {
  const source = `
package com.example;

@RestController
@RequestMapping("/orders")
class OrderController {
    @PostMapping("/{id}")
    Order update(@PathVariable Long id) { return null; }
}
`;
  const { symbols, relations } = relationsFor(source);
  const handler = symbols.find((s) => s.name === "update" && s.kind === "method")!;
  const route = relations.find((r) => r.kind === "ROUTE_TO_HANDLER" && r.sourceSymbolId === handler.id);
  assert.ok(route, "expected a ROUTE_TO_HANDLER relation for update()");
  assert.equal(route!.targetLabel, "POST /orders/{id}");
  assert.equal(route!.confidence, "exact");
  assert.equal(route!.family, "spring-mvc");
  assert.match(route!.evidence.join(" "), /RequestMapping.*orders/);
  assert.match(route!.evidence.join(" "), /PostMapping.*\{id\}/);
});

test("a method-only mapping with no class-level prefix has no leading artifact", () => {
  const source = `
@RestController
class HealthController {
    @GetMapping("/health")
    String health() { return "ok"; }
}
`;
  const { symbols, relations } = relationsFor(source, "src/main/java/HealthController.java");
  const handler = symbols.find((s) => s.name === "health")!;
  const route = relations.find((r) => r.sourceSymbolId === handler.id)!;
  assert.equal(route.targetLabel, "GET /health");
});

test("two overloaded handlers with the same HTTP method get distinct correct routes", () => {
  const source = `
@RestController
@RequestMapping("/pets")
class PetController {
    @PutMapping("/{id}")
    void update(Long id) {}
    @PutMapping("/{id}/vaccinate")
    void update(Long id, boolean vaccinate) {}
}
`;
  const { symbols, relations } = relationsFor(source, "src/main/java/PetController.java");
  const [first, second] = symbols.filter((s) => s.name === "update" && s.kind === "method");
  const r1 = relations.find((r) => r.sourceSymbolId === first.id)!;
  const r2 = relations.find((r) => r.sourceSymbolId === second.id)!;
  assert.equal(r1.targetLabel, "PUT /pets/{id}");
  assert.equal(r2.targetLabel, "PUT /pets/{id}/vaccinate");
});

test("a non-literal class-level path is not resolved and is marked unresolved, not guessed", () => {
  const source = `
@RestController
@RequestMapping(SomeConfig.BASE_PATH)
class DynamicController {
    @GetMapping("/x")
    void x() {}
}
`;
  const { symbols, relations } = relationsFor(source, "src/main/java/DynamicController.java");
  const handler = symbols.find((s) => s.name === "x")!;
  const route = relations.find((r) => r.sourceSymbolId === handler.id)!;
  assert.equal(route.confidence, "unresolved");
  assert.ok(!route.targetLabel || route.targetLabel.includes("SomeConfig.BASE_PATH"), "must not fabricate a path");
});

test("a same-class static final String constant resolves through one hop", () => {
  const source = `
@RestController
@RequestMapping(BASE)
class ConstController {
    static final String BASE = "/api/v2";

`;

  const route = relations.find((r) => r.sourceSymbolId === handler.id)!;

  assert.equal(route.confidence, "probable");
});
