# v1.5 Phase 3 → Phase 4 Recommendation

**Source:** `benchmarks/results/v1.5-phase3-rust-tasks.md` / `.json` (15 hand-written tasks, 5 per repository, over walkdir/mini-redis/ripgrep `crates/ignore`), Task 4's Phase 2 regression check (recorded in `.superpowers/sdd/2026-09-26-v1.5-phase3-rust-task-evaluation/task-4-report.md`, not committed — see note below).

## §75 rust-analyzer decision gate

The spec's gate: is rust-analyzer warranted only if (1) required facts are lost, (2) real tasks are harmed, (3) failures repeat across repositories, (4) structural analysis cannot reasonably solve them — all four.

- **(1) Required facts lost:** yes, initially — 5 of 15 tasks' facts were unreachable at the frozen baseline (fact recall 90.74%). After Task 4's three structural fixes (match-arm receiver typing, best-effort call recovery from macro arguments, cfg-duplicate handling), fact recall is 98.15% and only one fact in one task is still missing.
- **(2) Real tasks harmed:** the one remaining gap (`ripgrep-ignore-is-hidden-path-impact` / a `use` import line) does not fail the *task* — target found, retrieval recall 100% for that task, only one of several facts is missing text that sits outside any symbol's source. No task's target was ever unresolved after Task 4.
- **(3) Repeats across repositories:** the fixed causes each affected 2-4 tasks across 2-3 repositories (real repetition — this is why Task 4 fixed them, not one-offs). The one remaining cause affects 1 task in 1 repository.
- **(4) Structural analysis cannot solve it:** the remaining cause (a `use` line outside any symbol body) is solvable structurally — it needs a module-header/import-block context unit (§58), not rust-analyzer. Type inference for match-arm bindings and macro-argument call recovery, which looked like rust-analyzer territory, were both solved structurally in Task 4.

**Verdict: rust-analyzer is NOT warranted.** Every gate condition that was ever met (1, 3) has since been closed by structural fixes; the one remaining gap is a structural gap (an import line, not a call/type resolution problem), not a semantic one. §76 (no premature rust-analyzer) holds.

## Deferred areas, ranked by evidence

| Area (spec §) | Evidence | Verdict |
| --- | --- | --- |
| Module-header/skeleton context (§56-58) | The one remaining Phase 3 gap is a `use` line no symbol's source contains — a module-header context unit would close it. This is also the only gap left after Task 4. | **Justified** — smallest, most concrete win available; do next. |
| Cfg-alternative traversal (indexer, not language-specific) | Task 4's cfg fix attaches all `#[cfg(...)]` alternatives as probable targets, but the caller/callee graph traversal in the indexer only follows the first-listed one (documented limitation in the report). No task in this evaluation needed a non-first alternative, so it caused no measured failure — but it is a known half-fix. | **Weak evidence** — no task failed on it, but it is a latent gap should a future task need e.g. the Windows variant of a cfg-gated function. Worth a narrow indexer fix, not urgent. |
| Cargo/workspace resolution (§41-46) | None of the 15 tasks needed crate-name (`mini_redis::`) or workspace-path resolution — all pinned repos are single-crate or a sparse single-subsystem checkout, and no fact required it. | **No evidence from this phase** — the task set doesn't exercise it because the pinned repos don't need it. Not ruled out, just untested; a workspace-shaped repo would be needed to get evidence. |
| Composition skeletons (§57-58, general) | change/impact tasks (the categories most likely to want a compact skeleton) reached 100%/90.91% fact recall and 94.43%/91.14% median reduction without any skeleton — full sibling/caller/callee entries already fit comfortably under the smallest non-trivial budget (median minimum sufficient budget 256-2048 across categories). | **No evidence — defer.** Spec §57 itself says "only if benchmark evidence shows fact recovery value"; this evaluation shows the opposite for these tasks. |
| Macros/closures/attributes/cfg beyond Task 4's scope (§31-40) | Task 4 already added best-effort macro-argument call recovery (denylisted format/log/assert-style macros) and cfg-duplicate handling. No task in this evaluation exercised closures, `async`/`await` as a distinct edge, or `#[derive(...)]`/`#[serde(...)]` metadata. | **No evidence — defer**, except the already-flagged denylist gap (`anyhow!`/`bail!`/`ensure!`/`dbg!`/`matches!` — noted in code comment, low precision cost since capped to `probable`). |
| Tests/unsafe/lifetimes (§47-53) | No task in this evaluation targeted test code, `unsafe` blocks, or lifetime-sensitive APIs. | **No evidence — defer.** |
| Packaging/docs/version (§82-86) | Out of this phase's scope entirely; §84-86 (README, `docs/rust-support.md`, version bump to 1.5.0) are release-gating, not evidence-gated — every language phase before v1.5 did these once its behavior was evaluated, which is now true here. | **Do next, independent of evidence** — this phase's numbers are the material those docs need to cite honestly. |

## Recommended Phase 4 scope

1. Module-header/import-block context unit (closes the one remaining Phase 3 gap; small, evidence-backed).
2. README / `docs/rust-support.md` / version bump to `1.5.0` (release-gating, spec §84-86; cite this phase's numbers and known limitations verbatim, including the cfg-alternative-traversal and macro-denylist notes).
3. Packaging + clean-room smoke test (§82-83), since the adapter is otherwise feature-complete against the evidence gathered so far.
4. Not recommended without new evidence: Cargo/workspace resolution, composition skeletons, closures/derive metadata, test/unsafe/lifetime support, rust-analyzer.
